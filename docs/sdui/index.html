Server-Driven UI (SDUI)

WittyMediaServer describes the pages of its apps as data. An administrator says what Home holds, in what order, for whom; the server works out what that comes to for one profile on one device and sends a tree of components; the web app, the Apple apps and the Android apps each draw that tree with their own widgets. Re-ordering Home, giving Kids profiles their own Home, adding a page for film night or a row for one collection is a change on the server that every app picks up at once.

This document is the contract: the model, every component and data source, what a client sends, what it is sent, and exactly how it must draw it. The same thing for tools:

  • sdui.schema.json: a JSON Schema of everything sent and accepted, written from the code;
  • GET /api/v1/sdui/catalog: the catalogue as data, for editors;
  • pkg/sdui/conformance: fixtures that pin the contract down case by case, for renderers’ test suites.

The Go library behind it is pkg/sdui: pure Go, standard library only, no HTTP and no storage.

Settings is not part of this. Every app keeps its own Settings, built by hand. SDUI can link to it (a button, a navigation entry) and nothing more: there is no Settings page kind, and the navigation always holds the native Settings entry.

Design#

What it is now#

  • Semantic components. A page is a list of sections, each one a component a person would name: Hero, Shelf, Grid, DetailHeader, SeasonList, TrackList, FilterBar, Tabs, Banner, Notice, Text. Each renderer maps a component to its platform’s own idiom (a tvOS shelf with the focus engine’s lift and parallax, a Compose LazyRow, a CSS grid), which is what makes the result good everywhere. A small set of layout components (Stack, Split, Spacer, Divider, Button, Image, List) is there for pages of one’s own.
  • Data sources. A section says where its items come from by name: {"type": "recentlyAdded", "library": 3}, {"type": "genre", "genre": "Comedy"}, {"type": "collection", "collection": 12}. The server answers each with the library’s own indexed queries, through the profile’s limits, only for sections that are on the page, a page of items at a time. How an item becomes a card is fixed by the card’s style: nobody writes a field path.
  • Layers. Built-in pages; over them the administrator’s; a page per library, kind of library or kind of title; a variant for a kind of profile or device; conditions on any section; and each profile’s own order, hidden and pinned rows, density and card sizes, merged by the server.
  • A catalogue that describes itself, validation that says what to do, presets, a draft with a preview on a real device, import and export, history with a diff, and reset to default by deleting a page.
  • Navigation in the model, with Settings always present and always native.
  • Rules a renderer can be tested against. Sizes are abstract and resolved by the device profile; colours are theme tokens only; focus, states, truncation, labels and pictures are specified here and pinned down by fixtures.

Two things were deliberately left out. There is no expression language: conditions are a fixed set of fields, because anything else is code an administrator has to debug. And there are no scripts, no web views and no arbitrary addresses: a page can only open places in the app, the app’s own screens, and (where the device has a browser) a web page in the browser.

Designed for tvOS first#

An Apple TV is the strictest device a page has to work on, so the model is built around its rules and every other device gets them for free.

tvOS ruleWhat the model does about it
There is no pointer. Everything a person can act on must take focus, and focus must start somewhere.Every node a person can act on has focus.order in reading order and a focus.group; exactly one has focus.default. See Focus.
A page scrolls one way and its rows scroll sideways. Nothing scrolls both ways, and scrolling regions don’t nest.The components are that shape: a Page of sections, Shelf rows inside it. The validator refuses a row inside a row, and anything after the one NativeView or below a Grid that never ends.
Focus moves by direction, and guessing by geometry jumps between rows of different lengths.Movement between sections follows the page’s order and each group remembers its member; geometry is never used to pick a row.
The edge of a television picture can’t be relied on.layout.safeArea: 60 points top and bottom, 90 at the sides, on the 1920×1080 canvas.
It is read from the sofa.layout.text is the television’s type sizes (tv.type in themes/tokens.json: 57, 48, 38, 29, 25 points, and 76 for display) and cards are sized for three metres.
An Apple TV HD has little memory and a slow network stack.A page is cut to budget.maxSections; only the first budget.eagerSections rows arrive with cards, 12 a row; the rest are fetched as they come near.
A 4K poster in a 250-point card wastes all of it.Every picture’s address carries the width to ask for, from a short list of widths: 320 pixels for a poster on an HD, 640 on a 4K.
There is no web view and no browser.There is no web component; a button that opens a web page is not sent to a television.
The system has its own search keyboard, focus effect and player.SearchBox is the system’s field, a card takes the system’s focus effect, and playing is an action the app’s own player carries out.

Precedence#

What a profile sees on a page is decided in this order. Each step works on the result of the one before.

  1. The built-in page. Every stock page ships in the server (Built-in pages), written in this same model.
  2. The administrator’s page with the same ID replaces it whole. Deleting that page from the configuration brings the built-in one back (“reset to default”). Pages with other IDs are the administrator’s own.
  3. The most specific page of the kind asked for wins. For pages/library?library=3: a page whose match.library is 3, else one whose match.libraryKind is that library’s kind, else the page with no match. For pages/detail: match.mediaKind (and libraryKind) likewise. Among equals, the administrator’s page beats a built-in one.
  4. The first variant whose condition holds replaces the page’s sections. Variants are tried in order; none holding, the page’s own sections stand.
  5. Sections whose when doesn’t hold are dropped, and repeated sections become their copies (recent becomes recent-1, recent-2, ...: the section’s ID, -, the library’s, view’s or collection’s ID).
  6. The profile’s own arrangement is applied to the top-level sections: hidden ones go; pinned ones come first, in the order they were pinned; then the sections its order names, in that order; then the rest in the page’s order. A locked section is never hidden and never moves. A copy of a repeated section the profile never placed sits where the section it is a copy of was placed. Only what the page’s personal.allow lists is applied, and nothing is when the profile’s editLayout switch is off or the server has personalisation off.
  7. The device’s budget: sections past budget.maxSections are left out (layout.truncated), and data sections past budget.eagerSections arrive deferred.
  8. Each section’s source is asked, through the profile’s limits. A section with nothing in it is left out, unless it says "empty": "message".

Action#

A command action may carry confirm, a question to ask first (“Delete this memory?”): the client shows it with the command’s label as the confirming button and Cancel beside it, and runs the command only on a yes.

A navigate action may carry as: "layer": the page is shown over the current screen (a sheet, a quick menu, a dialog) and Back closes it, instead of replacing the screen. A client with no layers shows it as a page. Any page can be a layer; there is no separate kind.

Ignore an action type you don’t know.

A command’s request is built from its catalogue entry: put the action’s item, exactly as sent ("5", "show-5"), in place of {item}, URL-escaped in the path and JSON-escaped in the body, where it always stands inside a string ({"items":["{item}"]}), so the body is JSON for any title. The routes take a show’s show-<n> as they take a number: Watch later adds the show, watched.set and watched.clear mark every episode of it.

A command may take more values: its catalogue entry lists them as params (name, type of string, int, bool or ints, required). The action’s params give them by name, and each goes in place of {name} the same way: URL-escaped in the path, JSON-escaped inside the body’s string. For an int parameter the string and its quotes are replaced by the number ({"type":"save","slot":"{slot}"} becomes {"type":"save","slot":3}), A bool parameter is replaced the same way by true or false, an ints one (a list of numbers, such as the profiles a Kids profile may see) by a JSON array ([3,5]), and an object one (a collection’s rule) by a JSON object. A Form builds an object param from its controls named <param>.<key> (rule.yearFrom): each becomes a key of the object, a number field a number, an empty control no key, and a key ending [] (rule.genres[]) splits a comma-separated text into a list of texts. Either way the template is JSON. A parameter that wasn’t given is an empty string. rewind.open and controller.remap have no request: the game player opens its own panels.

Rules for renderers#

These are requirements. The conformance kit checks the ones that can be checked without pixels.

Unknown and future things#

  • An unknown type is drawn as a column of its children; unknown props and unknown top-level fields are ignored; an unknown action does nothing.
  • An unknown card style is drawn as its shape (poster, landscape, square, circle, chip): the picture, with the title and subtitle under it.
  • An unknown state is treated as ready.

Units, sizes and breakpoints#

  • Every size is in points: iOS and tvOS points, Android dp, CSS pixels. layout.scale is pixels per point and is used only to choose pictures.
  • Spacing is one of six steps (none, xs, s, m, l, xl); layout.spacing says how many points each is on this device. The distance between a page’s sections is l (m at the compact breakpoint).
  • Text is one of six roles (display, pageTitle, heading, title, body, caption; badge is a seventh, for badges); layout.text gives each one’s size. Use the platform’s dynamic type for the role where it has one; the numbers are the sizes at the default setting.
  • A row or grid says how big its cards are in props.card (width, height, aspect, shape): the size of the picture. Text goes under it.
  • Breakpoints are by the window’s width: compact under 600 points, medium under 840, expanded under 1200, large from there. layout.breakpoint is the one the page was rendered for. When the window crosses a breakpoint, ask for the page again with the new viewport.
  • Grid columns: props.columns is the count for the viewport sent. When the window changes without crossing a breakpoint, recompute: max(minimum, floor((content + gap) / (card + gap))), where content is the window’s width less the side margins (two m, or the safe area on a television), gap is m (s + xs at the compact breakpoint), and minimum is 2 (3 for cards under 130 points). Cards stretch to fill the row. A television’s grid has layout.cards[style].columns columns.
  • Content keeps inside layout.safeArea; where it is all zero, inside the system’s own safe area.

Focus#

node.focus is on every node a person can act on, and on nothing else.

FieldMeaning
orderIts place in reading order, from 1, without gaps. The same page gives the same numbers. Tab and Shift-Tab, and a screen reader’s next and previous, follow it.
groupThe ID of the row, grid, list, tab strip or row of buttons it is in. A group is one focus section: moving into it lands on the member that last had focus in it, else its first.
defaultExactly one node has it: focus starts there. It is a search box that asks for it, else the page’s DetailHeader, else the first focusable node that isn’t a tab, a filter bar or a search box, else the first of all.

Directional movement (a remote, a game pad, arrow keys in TV mode):

  • Inside a Shelf, left and right move between its cards and stop at the ends. Inside a Grid, the four directions move by row and column.
  • Up and down between top-level sections go to the previous or next group in order, landing on its remembered member. Geometry is never used to pick a row: the page’s order is.
  • A Hero, a DetailHeader and a FilterBar are one stop each: inside, left and right move between their own buttons or fields in the order given, starting on the primary one.
  • A deferred section takes no focus until its items have arrived; cards that arrive later join their group at the end, in the order sent.
  • With a pointer or touch, focus is only the keyboard order.

States#

stateWhat to draw
absentThe section, ready.
deferredThe section’s heading and placeholders, as if loading. When it comes within one screen of being seen, GET props.more.url: replace the placeholders with the items, merge props, and continue from next. If the answer’s state is empty, take the section off the page.
emptyThe heading and props.emptyText in the caption style where the items would be.
errorThe heading and one line, “Couldn’t load this”, with a Retry button that GETs props.more.url.

While any request is in flight a section shows placeholders: grey rounded rectangles of the card’s size, as many as are at least partly on screen (floor((content + gap) / (card + gap)) + 1, at most the row’s first page), pulsing unless motion is reduced. A whole page loading for the first time shows three such rows. A page that fails to load shows the app’s own error view with Retry; a 404 shows “This isn’t available” with a way Home.

Paging#

A Shelf, Grid, List or SeasonList with props.more has more items than it was sent. GET more.url when the person scrolls within one screen (a grid: two rows) of its end, with the same device parameters as the page. The answer is a SectionItems:

{ "version": 1, "section": "all",
  "items": [ { "type": "Card", "id": "all:161", "props": { "…": "…" } } ],
  "next": "/api/v1/sdui/pages/library-movies/sections/all/items?cursor=96&library=1" }

Append items to the section’s children; ask next in turn; no next means the end. With replace: true (another season) the items take the place of the ones there. props, present on a first page, are the section’s own props as they are now. Never ask for the same cursor twice at once.

Text#

  • The server has already cut text to the device’s limits (layout.textLimits): at a word where one is within 20 characters, with an ellipsis. A renderer shortening text itself (it shouldn’t need to) uses the same rule, sdui.Truncate.
  • Each card style allows its title and subtitle a number of lines (Card styles); a synopsis on a card gets 2, on a hero slide 3; a DetailHeader’s title 2 and overview 4, with “More” to read the rest. Past that, truncate with an ellipsis at the end.
  • Text is never scaled down to fit, and never scrolls sideways.

Pictures#

  • props.image is {url, width, height, aspect, kind}. Ask for url as it is: it already carries the width (?w=), chosen from layout.imageWidths as the smallest that covers the card at the device’s scale. Don’t ask for another size. A backdrop that spans the window (a title’s header, a hero’s slide) is chosen for the window’s width (the viewport sent, else the breakpoint’s usual window) at no more than two pixels a point, whatever the device’s scale: 960 on a 402-point phone. Only a real backdrop is sent as one: a title that has only a poster gets no image on a hero slide or banner and no images.backdrop in its header, never its poster stretched to 16/9; draw it on the theme’s colours.
  • Draw it in the card’s aspect, cropped to fill (cover), except a channel’s logo and a title’s logo, which are fitted inside (contain) on a plain tile in token bg3.
  • While it loads, and if it fails, fill its place with token bg3 and the item kind’s icon in token fg2. A card with props.icon and no image is drawn the same way on purpose.
  • Decode off the main thread and cancel when the card leaves the screen.

Colour and theme#

  • Renderers use the theme’s tokens (THEMES.md) and nothing else: no colour is ever in a page. Backgrounds bg, bg2, bg3; text fg, fg2; the focus ring, progress bars, selected tabs and primary buttons accent with accentFg on it; hairlines border; text over pictures onImage on scrim.
  • A node with tokens overrides those tokens for itself and everything in it; document.theme.tokens does so for the whole page. That is how a module’s colours, or a page’s own accent, reach a renderer: see Theme scopes.
  • Each component and card style says in the catalogue which tokens it is drawn with (tokens: colours by part, text roles, shape tokens), and GET /api/v1/theme has the values: colours (with the profile’s own and the colours derived from each override), shape (corner radii and the focus ring, in points) and type (typefaces and weights). A renderer draws from those and has no colour, corner or typeface of its own: see THEMES.md and the table. A node’s tokens are what its scope’s palette has that the account’s tokens don’t; with the automatic theme they are its dark look’s, so a client following the device takes variants[scheme].modules[scope].

Motion#

  • With layout.reducedMotion (the client sent capabilities=reducedMotion) a Hero has no autoAdvanceSec and must not move by itself; cross-fades become cuts; placeholders don’t pulse; focus effects keep their ring and drop their scale and parallax. A renderer also honours the system setting directly.
  • A Hero never advances while one of its buttons has focus or the pointer is over it, and pauses when it is off screen.

Accessibility#

Every component’s role and label derivation is in its entry under Components; the fixtures hold the exact strings. In short:

  • A card is a button (a link on the web) labelled with what its style shows, in the style’s order, joined by “, “: Film 3, 1993, 42 percent watched, 1 hr 1 min left. A title that isn’t drawn (a photo’s) is still in the label.
  • A row is a list labelled by its title; a grid a grid (a list on touch devices); headings are headings at levels 1 to 3 by role.
  • Touch targets are at least 44 points; a television’s buttons at least 66 tall.
  • Markdown is read as plain text: links by their text.

Components#

Every component in the catalogue is drawn by every renderer: there is no negotiation, no optional component and no fallback. The server never sends a tree in place of another; a client built for a catalogue revision other than the document’s catalog refuses the document. The only thing a client chooses is which native views it has for NativeView (views=); where it has none, the section’s own children are sent in a Stack.

Shell regions and what a page supplies to them#

Two regions of the shell are off in every look and belong to WittyPlay Online: statusBar (position top) and systemDock (bottom or side). A page turns them on by supplying content in its regions field, which is sent as document.regions (an administrator or a profile can still hide them with placements, and the placement of an experience or module scope turns them on too):

  • statusBar: up to six items, {id, kind, text}. kind is profile (the profile’s name, text the line under it), server (the server’s name drawn from the brand, so the coloured name survives) or text. The clock is drawn by every client, and so are a controller’s battery and its kind, from the device’s own Gamepad API: the server never sends them. Text may hold placeholders ({user}, {server}).
  • systemDock: up to seven round buttons, {id, label, icon, route, as, current}; the one whose route is the page showing is labelled under its button, or, on a page no button opens, the one marked current (a store under Settings). as: "layer" opens that page as a layer.

The regions stay while the module’s pages are showing (the same theme scope) and go when the person leaves them.

Forms and controls#

A List row can carry a control besides a route: control: {type, name, value, ...} in the row’s props, from an item’s control (a source’s, or a module’s: the server cleans it). Types: switch (value a bool), select (value a string, options the choices), field (value a string; placeholder, maxLength, multiline, input of text, number, url or search) and slider (value a number, min, max, step, unit). A disabled control is dimmed and takes no focus, and why says why in a line under it.

  • A switch row’s action is what flipping it does. The server has already put the new value in the action’s params (value, a bool), so a client never works out the opposite; after the command it asks for the page again, and the switch shows the stored state.
  • A select, field or slider row’s action is a command to run with the chosen value added to its params as value: a field on Enter or when it loses focus, a slider on release.
  • A row’s trailing text and action work as on any list row; a row with a control and no action is read-only.

A Form component (a container of Lists, Text and Notices with a submitLabel, an optional cancelLabel and one command) draws a Save and a Cancel at its foot instead: controls inside a Form run nothing when changed, and Save runs the Form’s command with every named control’s value under its name. See the Form entry in the component reference.

Detail panels, focusGrow and item actions#

A Shelf with focusGrow scales the focused card up (1.45 on a television, 1.25 on a tablet and desktop, none on a phone, whose first card is simply larger) and moves the cards after it aside; with reduced motion it gets a ring and no animation. A Shelf with detail draws a panel under the row for the focused item (the first until focus moves): the title large, the subtitle as one line, and the item’s actions as buttons carrying their key glyph (a select, b back, x and y the secondary and options keys of the shared pad map). A card carries props.actions ([{id, label, glyph, action}], at most four); an item with none shows title and subtitle, and the card’s own action is the A action. focusable on a Shelf, Grid or List makes a card with no action a focus stop anyway (a friend in a lobby). A person card draws a presence dot on its avatar from its badge text, by the card style’s badgeTones in the catalogue (Playing and Online ok, Away warn, Offline muted): the same on every app.

QR codes#

The QR component draws a QR code for a link, for a phone to scan (a room’s join link, a pairing address). Its value is a route of the app (/games?join=TIDE-4821) or an https address; with a source, the first item’s link is the value and its title the caption (a source whose item has no link gives nothing, and the section is left out: a room’s link is the host’s alone). The node’s props are value, isRoute, label and size (s, m, l): when isRoute is true the client makes the address absolute with the server’s own base address before it encodes it. Clients draw it black on white with a quiet zone of four modules and error correction M whatever the theme, because a scanner needs the contrast; the node takes no focus, and on a desktop the address is shown under it as selectable text.

Books and search filters#

A books library’s Books tab has a FilterBar with two more filters: reading (Reading, Finished, Not started: what the profile has started, finished or never opened) and format (Books, PDFs, Comics), and the grid’s books source follows them (filterable). A book’s page can list its formats with the formats source (the format that opens and the other files of the same name beside it, with sizes; never paths). On the search page a FilterBar with no target (narrow) offers Year and Score; every filterable search section follows them, so a film, show or anime library’s results are narrowed by the library’s own filters.

Empty sections that say what to do#

A Shelf, Grid or List with empty: "message" and nothing to show is drawn as an empty state: its emptyText, then the optional emptyHint (a line of advice) and the optional emptyAction (one button). The node has state: "empty" and props emptyText, emptyHint and emptyAction, where emptyAction is {label, action} and action is an ordinary action (navigate, native or a command, with as: "layer" and confirm as everywhere). The author gives the button a when condition, so only administrators are offered “Scan now” or “Add a games library” and everyone else sees the hint alone; the server has already applied it, so a client draws what it is sent. A page with no data should say what to do rather than draw a bare title: every client draws the empty state generically from these props, the same on every page. The built-in library pages for photos, books, games and other libraries offer an administrator library.scan (the library is the item).

The conformance kit#

pkg/sdui/conformance/fixtures holds one JSON file per case: an authored page, a request, canned data, the document the server must send for them, and the normalised layout a renderer must make of that document (what is visible in what order, cards per row, card sizes, columns, the picture each card asks for, text and line limits, labels, focus order and default). A renderer’s test suite reads the files, builds its views from expected.document, describes them in the normalised shape and compares with expected.layout. The README says how, for Swift, Kotlin and TypeScript. A renderer conforms when every fixture passes.

Personalisation#

A profile may arrange a page for itself. document.personal tells an app everything it needs to offer “Customise” without knowing the page:

"personal": { "editable": true, "allow": ["reorder", "hide", "pin", "density", "cardSize", "defaultTab"],
  "sections": [ { "id": "libraries", "title": "Your libraries", "pinned": true },
                { "id": "hero", "title": "Featured", "hidden": true },
                { "id": "onnow", "title": "On TV now", "empty": true },
                { "id": "setup", "title": "Notice", "locked": true } ],
  "density": "compact", "url": "/api/v1/sdui/pages/home/personal" }

sections are the page’s top-level sections in the profile’s order, hidden ones included so they can be shown again; empty ones have nothing in them now and aren’t on the page. The app shows that list, lets the person drag, hide and pin what isn’t locked, and PUTs the result to url:

{ "order": ["shuffle", "recent-1"], "hidden": ["hero"], "pinned": ["libraries"],
  "density": "compact", "cardSize": { "recent-1": "l" }, "defaultTab": { "views": "artists" } }
  • GET, PUT and DELETE on pages/{page}/personal and navigation/personal. Only ever the caller’s own.
  • Who may: any profile whose editLayout feature switch is on (it is by default; whoever manages a profile can turn it off with the other parental switches: PROFILES.md), unless the server’s personalisation.disabled is set. Otherwise editable is false, PUT answers 403 and what was stored is ignored, not deleted.
  • A page says what may be changed with "personal": {"allow": [...]}; an empty list is nothing. A section with "locked": true can’t be hidden or moved.
  • density is compact, comfortable or spacious: spacing at three quarters, as the device has it, or at five quarters. cardSize is s, m or l for a section.
  • The arrangement lives with the profile’s other interface choices (the same store /api/v1/me/ui reads, under sdui) and goes when the profile does. Home’s order and hidden rows from before pages were server-driven carry over: the built-in Home’s sections have the same IDs.

Profiles with limits#

Titles are one half of a profile’s limits (PROFILES.md), and every data source follows every kind of them: libraries, an age for each kind of media, genres hidden or the only ones allowed, tags, collections, single titles. How a row chooses its cards#

A section whose cardStyle is auto (or left out) takes its source’s usual style, with two refinements the server makes so every app gets them:

  • A source that gives whatever a library holds (recentlyAdded, browse, random, search, ...) on a library of music, audiobooks or podcasts draws album cards, on books book, on games game, on photos photo: the library is the section’s $each or the page’s own $library. A cover is never stretched into an upright poster.
  • On a phone, a row of the libraries (libraries source) drawn as tile is sent as chip: each library’s icon and name in a pill, a row a phone can take in at a glance.

A title’s page (detail) on a phone or a television carries no personal: nothing there offers Customise. A profile’s arrangement of the page, made on a bigger screen, still applies.

Books, statistics and likes#

Three sources fill pages that otherwise only the web app had, so a television or a phone draws them with the same Shelf, Grid and cards as everything else. No renderer needs to know them.

A books library’s shelf. books is the bookshelf WittyInk draws on the web: a books library’s books, narrowed to a series, an author or a format (epub, pdf or cbz: what each reader opens), by title, author (the books with none last), added (newest first), year (latest first) or series (each series in its own order, the books in none last); desc turns any of them round. With a series and no order, the series’ own order. A book’s series is its album and its place in it its track; its author is its album artist, else its artist, as the scanner reads them from the book. To give the shelf rows, repeat a section over bookSeries or bookAuthors: one copy per series or author of the page’s books library (so only on a library page), by name, with $each its name and {each} the title. The books in no series, or with no author, come last, as "~none" ($each then stands for it, and a source may name it outright), titled “No series” or “No author”. There are as many copies as the device’s budget for copies allows (Device profiles), the first by name. The built-in books library page has tabs for all three: every book, each series, each author.

A series’ name is free text, and two can be the same once cut down to what a node ID may hold, so each copy’s ID ends with a hash of the name rather than the name itself (in-series-1f0c4a7d2b9e3c11). Only the server uses it, to find the copy again for its next page.

GET /music/albums and GET /music/artists answer a books library too: its series (each with its author and how many books) and its authors. They used to answer nothing for one.

Statistics. statistics adds up the play log, most time first: the titles (stat: titles), the shows with their episodes together (shows) or each library (libraries, as tiles with how many titles), over the last week, month (the default), year or all time, in one library or all. Each card’s subtitle says how long, 3 h 20 min. A profile is shown its own record. "who": "everyone" is the whole server’s, with how many people watched each title, and is answered for administrators only: for anyone else it is empty, so the section is left out. It names and counts only what the profile may open now: a title it has since been kept from is neither shown nor added to a library’s time. Nothing leaves the server.

Likes. liked is what the profile gave a thumbs up (the like button on songs, videos and any title), most recently liked first, narrowed by media like continueWatching. It is the server’s favourites; a TV channel’s favourites are liveNow’s favourites.

What there is no source for.

  • Playlists are collections: a list someone made or a rule (the server’s smart playlists). collection gives one, collections all of them, and a row can be repeated over them. There is no separate playlist store.
  • Cast and crew. The library keeps no people: a film’s metadata keeps its director as one line of text (in title_meta), and nothing of its cast. The metadata lookups read the credits only to find that director. A people source (an item’s cast, the titles with someone in them) needs people stored with each title, and every title looked up again to fill them, so it isn’t offered rather than made up from one line of text.

Cast and crew#

Catalogue revision 5 adds who is in a title and who made it. Every built-in film, show and episode page has a Credits section right under its header (under the synopsis), and a person’s page shows their picture, dates, biography and their titles in this library.

The Credits component draws the credits source. Its children are person cards (style person), in this order: the cast in billing order, the guest stars, then the crew by department in the catalogue’s order (CreditGroups: Directing, Writing, Production, Camera, Lighting, Editing, Sound, Art, Costume & Make-Up, Visual Effects, Crew). Each card’s group is the part it is in (cast, guests, or a department’s key), its subtitle the part played or the job (“Production Design”, “Director, Screenplay”; a season’s guest star “Diver · 3 episodes”), its action opens /person/<id>. A person without a picture has no image: draw their initials on token bg3, hidden from assistive technology. props.groups lists the parts in order, {id, label, role, total, shown}; at first castLimit (20) of the cast and of the guests and crewLimit (6) of each department are sent, and when any part holds more, props.more is {url, label: "Show all"}: its answer has everyone, with replace true, in place of the cards you have. parts and departments choose what is shown.

Where the people come from, and what a profile may see: the source reads a title only after the title itself was found visible to the profile, and a season’s guest stars only from the episodes it may see. On an episode’s page the cast is its show’s regulars, the guests the episode’s own, and the crew the episode’s own where it names a department (the show’s otherwise). On a show’s page opened with ?season=<n> (a season’s page: the $season variable) the season’s guest stars come after the cast, most episodes first. See METADATA.md for the sources.

A person’s page is the detail page detail-person (match.mediaKind person), at the route /person/{person} (variable $person). Its DetailHeader (layout poster, no buttons) has the person’s photo as its poster, their name as the title, the biography as the overview, and the facts knownFor (“Acting”, “Directing”), born (“Born 3 February 1970, Lisbon”) and died. Under it one row per part of their work: a section repeated over personParts makes one copy per part the person has titles in that the profile may see (acting, then each department), $each the part’s key and {each} its label, and the filmography source gives that part’s films and shows, newest first, each card’s subtitle the year and the part or job (“2010 · as The Boss”, “2004 · Director”, “2019 · as Diver · 3 episodes”). A person credited only on titles the profile may not see has no page (404), as a hidden title has none.

Search finds people: the search source with in people gives person cards for names matching the query among people credited on titles the profile may see, the most titles first, each subtitled with what they are known for and how many titles (“Acting · 3 titles”). The built-in search page has a People row.

Requirements (PUT /sdui/config/experience, body {default, allowed, required: {everyone, kids, profiles: {"<id>": ...}}, profileThemes}) are {experience, theme}, either part or both, for everyone, for every kids profile or for one profile; the most specific wins part by part. The server stamps each with who set it and when. A required look is sent finished: GET /sdui/experience answers choice.required ({value, by, at, scope}) and editable: false, PUT /sdui/experience answers 403, and the theme engine’s look has requiredExperience and requiredTheme, so every client shows it locked (“Required by Willow”). allowed limits what profiles may pick and never overrides a requirement. Each profile chooses its own for each device (PUT /sdui/experience {experience}; DELETE to follow the server again). An app names itself with device= (or X-WMS-Device): a stable name of its own, letters, digits, - and _, never anything that identifies the hardware. experience= (or X-WMS-Experience) on a page, the navigation or the theme draws that one request with another experience, so an app can show a look before it is chosen; a requirement wins over it.

What a client is sent. Every page carries layout.shell and the navigation carries shell: {experience, nav, overlay, size, open, drawer}. nav is the menu’s style (sidebar, rail, railDrawer, bottomTabs, topTabs, floatingGlassBar, cableBar, bevelBar, teleKeys, crossbar, ornamentTabs, tvTopMenu, tvSideMenu), size its breadth in points, overlay that it lies over the top of the page, open how wide it is while open (a rail’s full menu, a television’s side menu) and drawer the width of a rail’s library drawer beside it (railDrawer only: choosing a library opens a second column headed by the library’s name, listing its views). An app draws its frame from the navigation’s shell and lays the page out in what is left; it never picks a style of its own and never switches on an experience’s id. The navigation also carries experiences: {current, chosen, options, url, required}, for an Experience row in the app’s own Settings (Settings is never SDUI). On a headset (formFactor=headset, platform=visionos or quest) the form factor is headset: ornament tabs, 60-point targets, nothing at the edges.

Placements. Everything in the shell is movable, by data. The shell is made of regions (brand, nav, search, profile, clock, dock, legend, hero), each with a position and visible (and the hero a style); the experience sets them, the administrator overrides them for everyone (placements in the policy, by experience) and a profile for its own device (PUT /sdui/placements), and the server sends the merged result in layout.shell.placements, so a renderer only draws it. The menu and You are locked: they can’t be hidden, so Settings and the way out are always there. Page sections are arranged by the page’s own personalisation (reorder, hide, pin, density, card size). The layout editor is each app’s own and drives these routes and personal.

What the server does for the app. An experience’s changes to pages are made in the document with the catalogue’s own components: a renderer that follows the document draws every experience with nothing more. Where it asks, a Hero becomes a Carousel (marquee), Home becomes a CrossBar of its rows (crossbar) or a WidgetGrid (dashboard), rows and grids become lists (compact, classicCable, retro), films’ and shows’ cards take the experience’s card style (plate, landscape, tile, block), headings take its heading style (band, underline) and See all becomes a row’s last card. The conformance kit has a case for every experience (exp-*.json).

The theme engine’s look carries the rest an experience brings: effects (glass, gloss, glow, texture and bevel, each none, subtle or full), shape, type set, density, motion, the WittyTV look it suggests, and the theme’s finish and scene.

Modules#

Every module carries its part of the apps in its own release, as data: its pages, rows on the built-in pages, named sections of its own, the data sources its helper answers, views of its own for NativeView, menu entries, settings and theme scope. The server checks them against this catalogue before a module is used and merges them in: a module’s pages come after the administrator’s and before the built-in ones, its rows go only into built-in pages, its menu entries sit before Settings unless the administrator placed them, and its components reach an app as the catalogue’s own. An app draws a module’s work with nothing of the module’s. SDUI for modules is the whole contract.

Theme scopes#

Colours come from the theme engine (THEMES.md); a page never holds one. A page or a section may say which scope it belongs to:

{ "id": "onnow", "component": "Shelf", "scope": "wittytv", "source": { "type": "liveNow" } }

A scope is a module’s ID (wittytv, wittymusic, wittyplay) or a name of the administrator’s own (family, evening). The colour overrides set for it with PUT /api/v1/theme/modules/{scope} (the theme engine’s module overrides, which accept any well-formed name) are sent as the node’s tokens, and as document.theme.tokens for a page’s scope. Items carry their own scope too: a channel’s card is in wittytv wherever it appears. A scope with no overrides changes nothing.

Text placeholders and Markdown#

Titles and text may hold placeholders: {user}, {greeting}, {library}, {each}, {title}. The server fills them in.

A Text with "format": "markdown" is sent as written and drawn from this subset, and nothing else: **bold**, *italic*, `code`, # to ### headings, - lists, 1. lists, blank-line paragraphs, and [text](to) where to is a route in the app or an http(s) address (opened in the browser; dead where there is none). Raw HTML is shown as the characters it is. The validator refuses a link that is neither.

Draft and preview#

ui_config.draft.json is a second configuration nobody is shown. Any page, navigation, preset or import route with ?target=draft writes to it (it starts as a copy of the published one). POST /sdui/draft/preview answers {"token", "expiresAt"}: a random token, good for two hours, for the administrator who asked and nobody else. That administrator’s apps send it as preview=<token> (or X-WMS-SDUI-Preview) with the page and navigation routes and are served the draft, with meta.source: "draft", on a real phone or television. Anyone else sending it gets 403. POST /sdui/draft/publish applies the draft to the configuration, as a new revision, and ends every preview; DELETE /sdui/draft throws it away.

Publishing merges. The draft remembers the published revision it was begun from (baseRevision). Publishing does not copy the draft over what is published: it takes what the draft changed since that revision, item by item (each page by ID, the navigation, the theme, the personalisation switch), and applies it on top of what is published now, so a change published after the draft was begun is kept. When the draft and what was published since changed the same item in different ways the answer is 409, nothing changes, and the body names them: {"error", "conflicts": ["/pages/home", "/navigation"], "baseRevision", "currentRevision"}. The editor reloads both, shows them, and publishes again with ?prefer=draft (the draft’s version of those items wins) or ?prefer=published (what is published stays; the draft’s other changes still go in), or edits the draft. When the revision the draft was begun from is no longer among the 10 kept, conflicts is ["/"] and only prefer=draft publishes (the draft as it is). If-Match keeps its meaning: the draft’s ETag.

Presets, import and export#

GET /sdui/presets lists ready-made pages and sections. A page preset is applied in one step (POST /sdui/presets/{id}/apply), then edited like any page; a section preset is a section for the editor to drop into a page. GET /sdui/export?page=<id> (or without page, everything) answers a file {"format": "wittymedia-ui", "formatVersion": 2, "kind": "page" | "config", ...}; POST /sdui/import takes one, into the draft unless target=published. dryRun=1 reports the issues and what would change, and changes nothing.

ui_config.json#

In the data folder. It holds only what an administrator changed:

{
  "version": 2, "revision": 7, "updatedAt": "2026-11-11T14:00:00Z", "updatedBy": "owner",
  "theme": { "tokens": { "accent": "#FF8800" }, "modules": { "wittytv": { "accent": "#2A6FDB" } } },
  "navigation": { "items": [ { "id": "home", "type": "page", "page": "home" } ] },

  • Strict. Unknown fields and trailing data are refused; at most 16 MiB and 200 pages; each key under pages is its page’s id; a page with a built-in page’s ID must be of the same kind. Every page and the navigation go through the validator; theme tokens must be colour tokens themes have, with colour values.
  • Revisions. Every save is a new revision, written atomically, with a copy of each of the last 10 in ui_config.history/. Rolling back makes an old one current as a new revision.
  • Edited by hand. Changing the file while the server runs is fine: on the next read it is validated and saved as a new revision (updatedBy: "file on disk"). One that doesn’t validate is kept as ui_config.json.bad and the last good configuration stays in force.

How the web client uses it#

The web app (web/src/sdui), which the desktop app shows unchanged in its own window, is one of the three renderers.

  • When. It asks /capabilities once per sign-in. With sdui-pages it resolves every address through the Routes table (routes.ts): an address that is a page is asked for and drawn; anything else is one of the app’s own screens. With sdui-navigation the side menu, the top bar, a phone’s bottom bar and TV mode’s top menu are drawn from GET /sdui/navigation, in the shell the app always had. Without those features (an older server) it keeps the pages and menu it worked out itself.
  • What it says it is. platform web (or desktop inside the desktop app), and a form factor from the window: TV mode is tv (deviceClass by the screen), a window under 600 points is phone, a touch screen under 1200 is tablet, anything else web or desktop. It sends viewport, locale, capabilities (reducedMotion from the system setting) and views=guide,photoTimeline,photoMap,coverFlow, and asks again when the window crosses a breakpoint.
  • The layout step. model.ts turns a document into a tree of views: what each component draws, its line limits, card sizes, placeholders, role and label. The React components (render/) take their props from those views, and the same step, described in the conformance kit’s shape, is what model.test.mjs runs against every fixture in pkg/sdui/conformance/fixtures.
  • Sizes. Card widths, grid columns, section gaps and spacing steps are the document’s (props.card, layout), set as CSS custom properties on the page; a television’s page is laid out on its 1920-point canvas and scaled to the window. Type sizes follow the app’s own scale for each text role, which grows with the reader’s browser setting. Colours are the theme’s variables; a node’s tokens override them for its subtree.
  • Keeping pages. A page is kept with its ETag and shown at once on the way back to it, then asked for through /diff?since=; patches are applied to the kept tree (patch.ts), and anything that doesn’t apply drops it. It is asked for again after meta.ttlSeconds while the tab is visible, and after a command or a change to the profile’s arrangement. Rows that had been filled or paged stay filled when the page comes again.
  • Focus. Tab order is the document’s order. In TV mode, and with a game pad or arrow keys anywhere, focus.ts decides where an arrow goes from focus.order and the groups: along a row and stopping at its ends, by row and column in a grid with the column count as drawn, up and down to the previous or next stop and the member it was left on. Focus starts on focus.default.
  • Actions. navigate is a link; play asks what the item is and starts the app’s own player for it (video, disc with its menus, audio as the album from that track, reader, game); native opens Settings, the guide, You, the share dialog, the device picker, a watch party or a download; external opens a new tab; command calls the route in Commands and asks for the page again; selectTab and the filter bar change the address’s query, so Back undoes them.
  • Native views. guide is the guide’s grid, photoTimeline and photoMap the photo library, coverFlow the music library’s cover flow. A module’s view (<module>.<name>) is drawn by its web bundle, and the app sends the views of the bundles in use with its own (Modules in server-driven UI).
  • Experiences. The frame follows the navigation’s shell, whatever the experience (see Experiences). The app names itself with device=, a random name kept in the browser. Settings, Appearance offers the experiences, themes and Import a theme; Settings, Pages & menu, Experiences is the administrator’s config/experience, with the required looks.
  • Modules. Their settings are under Settings, Module settings, drawn with Settings’ own rows; their pages of the app’s own (/m/...) and their views take the module’s colours where its palette differs from everyone’s.
  • Where the app’s own screens stand in. A game’s page, a book’s front page, a photo, a radio station, a creator’s channel and the short-video feed are not in the model. When the catch-all built-in library or detail page is what the server answers for one of those, the web app shows its own screen for it (native.ts); a page an administrator wrote for such a library or title is drawn as written. Under a title’s header the app adds what the model has no component for: the credit a metadata source asks for, the file’s technical facts, a disc’s titles and extras, and, for administrators, artwork, details and refresh (for a show also “Find intros and credits”). Above a show’s episodes is the Cards or Playlist switch (an administrator’s choice is kept for the show).
  • The app’s own tools. Under the title of a library of films or shows: Filters with every filter of the app’s Filters panel (the page passes them on: series, kind, disc, minRating, audio, subtitle, format, edition, search, seed beside the filter bar’s own), saving a view and the saved views, and for administrators Select (to edit titles together), Categories, Fix matches and Scan. A music library has Play all, Songs and Playlists (those two open the app’s own music page on that tab) and Scan; Collections has New collection; a collection has Play all, Edit, Remove titles and Delete (extras/PageTools.tsx).
  • Customise and the editor. document.personal drives “Customise this page”; the menu’s personal drives “Arrange the menu” in Settings, Appearance. The administrator’s editor is Settings, Pages & menu, built from GET /sdui/catalog. Both are described for the people using them in PAGES.md.
  • What carried over. Home’s order and hidden rows (/me/ui home) are read by the server. The web app’s own menu arrangement (/me/ui nav) is moved once: its order and hidden entries become navigation/personal, how the menu is drawn (grouping, overflow, folding) stays a choice of the web app’s own (navLook), and the old record is removed.

Performance and limits#

  • Only what is on the page is read. A section’s source is one or two of the library’s indexed queries, asked for one page of items. Sections past the device’s eagerSections aren’t asked at all until the client wants them, nor are sections after many empty ones.
  • Small payloads. A television gets 4 filled rows of 12 cards (6 of 20 on a 4K one) and fetches the rest as they are approached; text is cut to the device’s limits; pictures are asked for at the size they are drawn.
  • Renders are kept briefly. The same request from the same profile within 3 seconds (a page and its diff, an app starting up) is one render. Longer would need a version number for the library’s data, which the store does not have; ETag and 304 make the repeat cheap for the client either way. A profile’s own change to its arrangement drops its kept renders at once.
  • Bounded memory. Renders kept for diffs, recent renders and preview tokens are capped, lower on small machines.
  • Limits on what is authored: see Limits.

Security#

  • No scripts, no web views, no addresses of one’s own. A page can open routes on this server, the app’s own screens and, in the browser, an http(s) page. Pictures are paths on this server. Markdown is a fixed subset with the same link rule. The validator refuses the rest, and a renderer never interprets HTML.
  • Every item is read through the profile’s limits: library, rating, title and collection limits, Live TV and feature switches. A page that names a library the profile can’t open shows it nothing; a page about something it can’t see is not found. This is checked for every built-in page, for sections’ own pages of items, and for pages an administrator wrote to name a library outright.
  • Buttons follow the profile’s feature switches: a profile that may not download or share isn’t offered either.
  • Configuration is for administrators, with If-Match against lost updates. A profile’s arrangement is written only by that profile, only when its editLayout switch allows.
  • A preview token shows the draft only to the administrator it was made for.
  • Caps on sizes, depth and counts everywhere (Limits).

Versioning#

  • version (1) changes only for something a client built for it can’t survive. Clients refuse a version they don’t know.
  • The catalogue revision (8) counts changes to the catalogue. The rule: any change to what an existing component or card style shows or does bumps the revision (a card style that gains badges, a property that changes meaning, a component that draws something else). Only a new component, card style, source, command, condition, action type or optional property is additive, and keeps the revision it came in. Client and server must be built for the same revision. Unknown props and actions are ignored, an unknown card style is drawn as its shape.
  • Where a client gets the card styles. From GET /api/sdui/catalog, which it fetches at sign-in and when the revision changes (the web app does). A table of them built into the app is only for offline tests, and a conformance test must check it against the catalogue the server serves (see the conformance kit), so a change to what a style shows can’t be missed.
  • ui_config.json has its own version (2).
  • The conformance kit has a kit number; a change to a fixture’s expected output is a change to the contract and is called out in the changelog.

The music table#

GET /api/sdui/catalog carries music (pkg/sdui/data/music.json): the mini player’s controls and the visualizer’s. music.visualizer.presets are the effects the effects picker offers, the same as WittyVisualizer’s effects/*.glsl (the 17 classics and Aurora Rings, in the order of its README): {id, name, motion, calm, cost}. motion is gentle or lively, calm is true when calm mode keeps the effect (the gentle ones; it is on by default when the system asks for reduced motion), cost is how hard it works the graphics card (1 to 3). Theme tokens#

Every colour, typeface and corner comes from the theme: colours from GET /api/v1/theme tokens (with a node’s scope tokens over them), corners from its shape, typefaces and weights from its type, sizes from layout.text. A renderer has none of its own. Each component and card style has tokens in the catalogue: which colour token each part is drawn in, which text role each piece of text takes, and which shape token rounds each part. THEMES.md explains them.

Text roles: badge (body family, strong weight), body (body family, body weight), caption (body family, body weight), display (display family, heading weight), heading (display family, heading weight), pageTitle (display family, heading weight), title (body family, strong weight).

Colour roles:

  • background: What the component fills its own area with.
  • surface: A raised area inside it, and the place of a picture that hasn’t loaded.
  • text: Its main text.
  • secondaryText: Subtitles, facts, inactive tabs.
  • hintText: Numbers, placeholders, hints.
  • link: Links and highlighted words: the accent as text.
  • icon: Icons beside text.
  • accent: Filled things that stand out: a primary button, a selected tab’s underline.
  • onAccent: Text and icons on accent.
  • accentHover: accent while hovered or pressed.
  • selected: The tint behind a selected row or chip.
  • selectedBorder: The outline of a selected chip.
  • selectedText: The text of a selected tab, chip or row.
  • hover: The tint over a hovered row (pointer devices).
  • pressed: The tint over a pressed row.
  • border: Hairlines.
  • outline: Outlines of secondary buttons and chips.
  • fieldOutline: Outlines of text fields and other controls: 3:1 on every surface.
  • focus: The focus ring.
  • onImage: Text and icons over a picture.
  • scrim: The plate behind text over a picture.
  • badge: A badge’s fill (over a picture).
  • badgeText: A badge’s text.
  • progress: A progress bar’s filled part.
  • progressTrack: A progress bar’s empty part.
  • watched: The watched mark’s fill.
  • onWatched: The watched mark’s tick.
  • playing: The track or item playing now.
  • info: The information tone’s bar and icon.
  • success: The good-news tone’s bar and icon.
  • warning: The warning tone’s bar and icon.
  • danger: The problem tone’s bar, icon, and a destructive button.
  • dangerTint: The tint behind a hovered destructive button.
  • brand: The server’s name, its coloured parts (brandParts with accent).

Shape tokens:

  • card: Cards and their pictures.
  • button: Buttons.
  • field: Text fields, selects, search boxes.
  • row: List rows.
  • thumb: Small pictures in a row.
  • chip: Chips and filter pills.
  • badge: Badges and small labels.
  • image: Pictures and banners placed on a page; the spotlight on a television.
  • sheet: Menus, popovers and sheets.
  • dialog: Dialogs.
  • pill: Fully round whatever the size: a circle on a square picture.
  • focusWidth: The focus ring’s width.
  • focusOffset: The gap between the focus ring and what it surrounds.
