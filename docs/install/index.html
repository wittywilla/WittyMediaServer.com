Installing WittyMediaServer

Install the server on Windows, macOS, Linux, FreeBSD, a NAS or in a container, keep it up to date, and find out what each program does.

FFmpeg comes with the download, so there’s nothing else to install first, apart from one FreeBSD case noted below. To check a computer is enough, see What hardware it needs. New to all this? Getting started walks through it with no command line. To remove it, see Uninstalling.

Which file to download#

Everything is on the project’s Releases page. Most people want the installer. Each file name starts wittymediaserver-<version>-, followed by what’s in the table.

These files are the server, for the computer that holds your media. For a phone, a TV or another computer, you don’t install the server. Open the server’s address in a web browser, or use the app, WittyMediaClient, which has its own Releases page. The app is written for Windows, macOS, Linux, FreeBSD, Android, Android TV, iOS, tvOS and Plasma Big Screen, but it’s early: Android has been run on emulators only, and iOS and tvOS have never been built. A web browser is the way to reach everything today. Apps and devices has the state of each device.

Each release also has SHA256SUMS.txt, a list of every file’s checksum, and SHA256SUMS.txt.sig, its signature. The server checks that signature before it installs an update.

What has been tested#

SystemHow far it has been run
WindowsThe .msi has been installed on Windows 11, and upgraded and removed under Wine. Before each release it’s installed over the one before on GitHub’s Windows machines, for everyone, for one account and as a service, with the server running. The ARM64 .msi was built once and hasn’t been checked
macOSNever built or run. This has not been run on a real Mac yet
LinuxThe .deb and .rpm have been installed, upgraded and removed on Debian trixie, Ubuntu 26.04 and Fedora 43, on amd64, in containers with systemd running. The arm64, armv7 and 386 packages haven’t been run
FreeBSDThe amd64 package and its service have been installed, upgraded and removed in FreeBSD 14.4 and 15.1 virtual machines. Real hardware and arm64 haven’t been tried, modules have only been built for it, and a film hasn’t been played there
DockerThe amd64 image has been built and run in WSL, locked down, as several users, upgraded from 0.6.2-alpha, with NVENC through WSL. arm64 and armv7 have been built, not run. No NAS yet. See Docker

Windows#

  1. Open the .msi. If Windows warns about it, see Warnings you’ll see.
  2. Choose who it’s for.
Just meEveryone on this computer
Needs an administratorNoYes
Program%LOCALAPPDATA%\Programs\WittyMediaServerC:\Program Files\WittyMediaServer
Library, accounts and settings%LOCALAPPDATA%\WittyMediaServerEach person’s own, or with the service, C:\ProgramData\WittyMediaServer
Update now in SettingsYesNo: Download the installer there, then run it
Can run as a serviceNoYes
  1. Choose how it should run. Each of these is optional.
    • Start when I sign in: the tray app starts by itself. You can turn this off from its icon. If it’s installed for everyone, turn it off in Windows Settings, under Apps, Startup.
    • Put a shortcut on the desktop. There’s always a Start menu entry.
    • Add the wittymediaserver command to the command line, in every new terminal.
    • Run as a background service, always on (for everyone only): it runs even when nobody is signed in, under the limited LOCAL SERVICE account. See below for what it needs.
    • Let other devices on my home network connect (for everyone only): adds a Windows Firewall rule for networks you’ve marked private. It opens nothing to the internet, and as it’s for the server program, it goes on working when you change the port. Installed just for you, Windows asks when the server first starts: choose Allow.
  2. Leave Open WittyMediaServer now ticked to finish setting up in your browser.

Running a newer installer over an installed copy updates it in place and keeps your choices. It also takes over from a copy that 0.5.2-alpha or older installed: the old program, boot task and firewall rule go, and your library stays where it is.

If you chose the service. Give LOCAL SERVICE permission to read your media folders: open a folder’s Properties, then Security, Edit, Add, and type LOCAL SERVICE. It can’t reach a network share by a mapped drive letter, so use \\server\share, on a share that lets it in.

For admins. Every choice is a property, and /qn asks nothing. Without a choice of who it’s for, it installs just for the person running it.

msiexec /i wittymediaserver-<version>-windows-amd64.msi /qn MSIINSTALLPERUSER=1 AUTOSTART=1 DESKTOPSHORTCUT=1 ADDTOPATH=1
msiexec /i wittymediaserver-<version>-windows-amd64.msi /qn MSIINSTALLPERUSER="" INSTALLSERVICE=1 ADDFIREWALL=1 AUTOSTART="" PORT=8096
PropertyMeansIf you don’t say
MSIINSTALLPERUSER1 for this account, "" for everyoneThis account
AUTOSTART1 starts the tray app at sign-in, "" doesn’t1
DESKTOPSHORTCUT, ADDTOPATH1 adds itOff
INSTALLSERVICE, ADDFIREWALL1 adds it, for everyone onlyOff
PORTThe port, saved in settings.ini in the data folder: the service’s, or the installing account’sWhat it was: 9797 on a new install, and on an upgrade, the port the service had

Without installing. Unzip the .zip anywhere and open WittyMediaServer.exe. Add a wms.json beside it to keep everything in that folder, on a USB drive for instance.

macOS#

This has not been run on a real Mac yet.

  1. Open the .pkg. If the Mac refuses it, see Warnings you’ll see.
  2. Go through the installer. It puts WittyMediaServer and Uninstall WittyMediaServer in Applications, and the wittymediaserver command in /usr/local/bin.
  3. Customize lets you leave out Run in the background, which otherwise starts the server when the Mac starts, as the person who installed it, even when nobody is signed in. Without it, the server runs while the app is open.

Your library, accounts and settings are in ~/Library/Application Support/WittyMediaServer.

Running a newer .pkg updates it in place, and takes over from what the install.sh of 0.5.2-alpha or older put in /opt, keeping its library.

A limit on a Mac. A module’s helper program runs in Apple’s own sandbox, which hasn’t been run on a real Mac yet, and Settings, Modules says if it couldn’t be used. So a module from another publisher can’t be chosen on a Mac for now. See Modules.

Without installing. Unpack the .tar.gz and open WittyMediaServer.app.

Linux#

sudo apt install ./wittymediaserver-<version>-linux-amd64.deb    # Debian, Ubuntu and relatives
sudo dnf install ./wittymediaserver-<version>-linux-amd64.rpm    # Fedora, RHEL and relatives

That’s all: the service is running. Open http://<this computer>:9797/ to finish setting up.

There’s no package repository to add yet, so apt upgrade and dnf upgrade won’t find new versions. Download each new package and install it the same way: it updates in place. It also takes over from what the install.sh of 0.5.2-alpha or older installed, keeping its data folder, port and account.

To see or changeWhere
Its status and logsystemctl status wittymediaserver, journalctl -u wittymediaserver
Program/usr/lib/wittymediaserver, with the command at /usr/bin/wittymediaserver
Library, accounts and settings/var/lib/wittymediaserver
The account it runs aswms, which needs read permission on your media folders
The portSettings → Network, or /var/lib/wittymediaserver/settings.ini: see The port
The data folder or anything elsesudo systemctl edit wittymediaserver

A port set with systemctl edit before 0.7.0, as WMS_LISTEN, moves into settings.ini when you install this version. For a different data folder, set both of these, as the service can only write where it’s told:

[Service]
Environment=WMS_DATA_DIR=/tank/witty
ReadWritePaths=/tank/witty

A desktop gets WittyMediaServer in its app menu. The tray app shows the service, and doesn’t start a second server.

On another distribution, with systemd. Unpack the .tar.gz, and:

sudo ./install.sh                      # /opt/wittymediaserver, data in /var/lib/wittymediaserver, port 9797
sudo ./install.sh --prefix /srv/witty --data /tank/witty --port 8080 --user media

Without installing. Run ./WittyMediaServer, or ./bin/wittymediaserver serve with no tray icon.

Run either a service or the tray app on a port, not both by hand. The tray app notices a server already answering, and only shows it.

FreeBSD#

As root:

pkg add wittymediaserver-<version>-freebsd-amd64.pkg
sysrc wittymediaserver_enable=YES
service wittymediaserver start

Then open http://<this computer>:9797/ to finish setting up. As with FreeBSD’s own packages, it doesn’t start until you enable it. If it says FFmpeg is missing, run pkg install ffmpeg. The arm64 package always needs this, as there’s no FFmpeg build of ours for it.

To see or changeWhere
Program/usr/local/lib/wittymediaserver, with the command at /usr/local/bin/wittymediaserver
Library, accounts and settings/var/db/wittymediaserver, and the log is wms.log in there
The account it runs aswms, which needs read permission on your media folders
The account or data foldersysrc wittymediaserver_user=media, sysrc wittymediaserver_data=/tank/witty
The portSettings → Network, or /var/db/wittymediaserver/settings.ini: see The port. wittymediaserver_listen from before 0.7.0 moves there when you update
A settings file/usr/local/etc/wittymediaserver/wms.json

To update, run pkg add -f with the newer package, then service wittymediaserver start, as pkg stops it. It also takes over from what install.sh installed, keeping its data folder, port and account. A package made for FreeBSD 14 needs env IGNORE_OSVERSION=yes pkg add <file> on 15, which hasn’t been tried.

A limit on FreeBSD. A module’s helper program runs with limits here, not a sandbox: it can’t start programs, open a network connection or write into a file, but it can still read what the account can read, delete its files and signal its programs. So run the server as its own account, as the package does, and a module from another publisher can’t be chosen, and WittyCouch isn’t available, as its host has no FreeBSD build. See Modules.

Without a package. Unpack the .tar.gz and run ./install.sh as root, with the same options as on Linux. It starts the service straight away.

Docker#

docker run -d --name wittymediaserver --restart unless-stopped   -p 9797:9797   -v wms-config:/config   -v /path/to/media:/media:ro   ghcr.io/wittywilla/wittymediaserver:alpha

Then open http://<this computer>:9797/. From another device, setup asks for the code that docker logs wittymediaserver shows.

Docker has the rest: ready compose files (plain, locked down, Intel and AMD graphics, NVIDIA, behind a reverse proxy), the tags, every folder and setting, running as your own user, hardware transcoding, and updating. The image is for amd64, arm64 and armv7, runs as an ordinary user, and works with a read-only root.

Another port: change the first number of the published port, such as "8096:9797", and run docker compose up -d. Inside the container it stays 9797, so Settings → Network can’t change it.

What the programs are#

You only ever need to open the first one.

ProgramWhat it does
WittyMediaServer.exe (Windows), WittyMediaServer.app (Mac), WittyMediaServer in the app menu (Linux)The app you open. Puts an icon in the tray or menu bar, starts the server and opens the web app
Uninstall WittyMediaServer.exe, Uninstall WittyMediaServer.appRemoves it, asking first. See Uninstalling

On Windows each says what it is in its Properties, and in Task Manager’s Details. On a Mac the same programs are inside the app, under Contents/MacOS and Contents/Helpers, and modules under Contents/Resources.

An icon appears in the system tray or menu bar. It turns grey while the server is stopped.

The app restarts the server if it crashes. It stops trying after three failures within ten seconds of starting, so a bad configuration doesn’t loop.

Updating#

Admins see a banner at the top of Home and Settings when a newer version is out, with its first change in a few words: Update, What’s new, or Later, which hides it until the next version. The activity panel, the account menu and the tray icon’s menu say so too, and Settings has a dot. Settings → About, under Updates, shows the installed and the newest version, and what’s new in every version since yours, from this changelog. Update now installs it:

  1. Downloading: the release’s checksum list and its signature come from GitHub, over HTTPS, and only from GitHub.
  2. Checking: the checksum list must be signed with the release key built into the server, and the downloaded package must match its checksum. Anything else is refused and nothing changes.
  3. Installing: the new files are unpacked next to the program and swapped in. The data folder, wms.json and any other folder the server keeps data in are never written.
  4. Restarting: the tray app, systemd or the server itself starts the new version, and the page reloads by itself.

The server looks for new versions twice a day while Check for updates automatically is on, which it is to begin with. Check now asks at once. It only fetches GitHub’s list of releases: nothing about you or your library is sent, and nothing is installed until an admin presses Update now.

Update now needs a copy installed from a release package, in a folder the server can write. Otherwise there’s Download the installer: the server fetches the right file for its system and processor from the release, checks it against the release’s signed checksums the same way, and keeps it in its cache folder. Settings then says where it is, gives the command that installs it where there is one, and offers Save the installer to save it on the device you’re using.

Installed withHow to update
Windows installer, Just me, or an unpacked folder on Windows, Linux or FreeBSDUpdate now
Windows installer, Everyone on this computerDownload the installer, then run it on the server’s computer, as Windows protects Program Files. It updates in place
.deb, .rpm, FreeBSD .pkgDownload the installer, then run the command Settings shows (sudo apt install …, sudo dnf install … or pkg add -f …), as your package manager owns these files. The server never runs it itself
install.shDownload the installer (the archive), unpack it and run sudo ./install.sh again
macOSDownload the installer, then open the .pkg
Dockerdocker compose pull, then docker compose up -d. With docker run: docker pull, then remove and recreate the container. Your /config volume stays

A copy of 0.5.2-alpha or older takes the update as well, from a folder it can write. The server moves to bin/ at the same time, and a small wms stays where the old server was, so whatever started it still can. Scripts of yours that call wms should change to wittymediaserver. In Docker that name has already gone.

At home and away#

WittyMediaServer runs on your own computer, in your home. Out of the box it’s available on your home network only: every device on the same Wi-Fi or cable network can open http://<this computer's address>:9797. The setup wizard and Settings → About show the address, and Settings → Network changes its port.

Setting up from another device. Until the first account exists, whoever makes it owns the server. On the computer running it, setup just works. From any other device, your phone included, setup asks for a setup code, because someone else on your network could otherwise get there first. Find it in either place:

  • on the server’s console when it starts (This server has no accounts yet..., in docker logs or journalctl -u wittymediaserver);
  • in setup-code.txt in the server’s data folder, which goes away once setup is done.

It’s never kept in the log files or shown in the log viewer. If you trust everyone on your network and would rather not use it, set setupFromHome.

A server nobody can reach from a home network first, such as a rented one, also needs remoteAccess turned on, and HTTPS.

If other devices can’t connect on Windows. The installer’s firewall rule covers networks you’ve marked private, not public ones. Set your network to Private in Windows’ network settings.

If other devices can’t find or connect on a Mac. The first time the app starts the server, macOS asks whether WittyMediaServer may find devices on local networks. Choose Allow. If you didn’t, turn it on in System Settings → Privacy & Security → Local Network. The server notices within a minute.

Away from home. It works once you turn on Settings → Remote Access and follow its steps. Until then the server refuses connections from outside your home, even if your router lets them through. Remote access explains each way in: a private VPN, which is the easiest and safest; forwarding a port with HTTPS; your own reverse proxy; or a rented server. The server refuses unencrypted connections from the internet, so use HTTPS, and strong passwords for every adult profile.

Behind a reverse proxy#

WittyMediaServer serves plain HTTP, so put Caddy, nginx or Traefik in front for HTTPS. Video segments are a few MB each and long requests are normal, so turn off body-size limits and raise read timeouts. Set WMS_PUBLIC_URL or publicUrl to the outside address, and list the proxy in WMS_TRUSTED_PROXIES or in Settings → Remote Access: forwarded headers are believed from nobody else. See A reverse proxy you already run.

media.example.com {
    reverse_proxy 127.0.0.1:9797
}

Warnings you’ll see#

The programs in this alpha aren’t code-signed yet, so systems warn about them. Everything works once you get past the warning. Each download’s checksum is in SHA256SUMS.txt, if you want to check it.

SystemWhat you seeWhat to do
Windows“Windows protected your PC”, from SmartScreenChoose More info, then Run anyway
Windows 11, with Smart App Control onWindows blocks the installer, and offers only to turn Smart App Control offDon’t turn it off: Windows can’t turn it back on without being reinstalled. Signed releases are being prepared. See Smart App Control on Windows
Windows, for everyoneThe administrator prompt says “Unknown publisher”Choose Yes if you trust the download
macOSThe Mac refuses to open the .pkgRight-click it and choose Open, then Open again. If it still refuses, choose Open Anyway in System Settings → Privacy & Security
Linux, FreeBSDNothing, for a file you install by nameNothing. The packages carry no signature of their own

For developers#

Kubernetes. deploy/k8s in the source has a setup: kubectl apply -k deploy/k8s. Edit deployment.yaml for your media volume (NFS, hostPath or CSI) and ingress.yaml for your hostname and TLS. The deployment uses Recreate, as SQLite has one writer, and an in-memory emptyDir for transcoding. The config volume holds the database and artwork. It uses the latest image, which exists once there’s a full release, so set newTag in kustomization.yaml to alpha until then.

Making the installers, and everything about signing: docs/PUBLISHING.md and scripts/test/README.md in the source.
