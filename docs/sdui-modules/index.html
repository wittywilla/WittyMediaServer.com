Modules in server-driven UI

A module’s part of every app is data that ships with the module. Its pages, its rows on Home, its menu entries, its data sources, its settings and its colours are written in one file, sdui.json, in the module’s own repository. The server checks the file against its catalogue and merges it into what every app is sent. No app needs any of the module’s code to show it.

This document is the contract for that file: what goes in it, what the server checks, what it does with it, and what apps and module helpers must do. It builds on Server-Driven UI, which describes pages, sections, components, sources and conditions; this document links to it rather than repeat it. How modules are built, released and run is in Making a module.

The worked example throughout is a made-up board games module, wittyboardgames. Its whole file is pkg/sdui/testdata/module-boardgames.json, and The worked example, end to end walks through it.

What and why#

Before this, what a module added to the apps was code in each app, or a web page only the browser could show. A television app had to be released again for every module, and a module written by someone else could not reach it at all.

Now a module describes what it adds with the catalogue’s own components. The server expands and renders it like any other page, so:

  • It is portable. Every app that draws the catalogue draws every module, today and later, with no release of the app.
  • It lives with the module. The file is in the module’s repository and in each of its releases. A new release of the module can change its pages without a new server.
  • It is checked. The server refuses a file that doesn’t fit its catalogue before the module is used, so a broken module never breaks a page.
  • It is safe. It is data, never code. A module’s items pass through the profile’s limits like the server’s own.

Settings are the one exception to “it is SDUI”. A module describes its settings as rows, and each app draws them in its own Settings, in its own style. Settings is never an SDUI page (SDUI.md).

Module API 4#

Module API 4 makes sdui.json part of a module. The numbers are in internal/modules/sdui.go:

ConstantValueWhat it means
API4The newest module API this server takes.
MinAPI3The oldest. A version built for API 3 still runs.
SDUIAPI4From this API on, a module must carry sdui.json.

Which versions must carry the file:

api in module.jsondeliverysdui.json
4 or morehelper, program, webRequired. A version without one is refused, unless an administrator overrides that (kind incomplete); it then runs without its SDUI.
4 or morelibrary, builtinNot read. A library reaches the server inside other modules.
3anyOptional. API 3 modules keep working until they are upgraded. One that carries sdui.json anyway has it checked and used.

A module with nothing to add to the apps still carries the smallest file:

{ "format": "wittymodule-sdui", "formatVersion": 1, "module": "wittyx", "catalog": 2,
  "theme": { "scope": "wittyx" } }

The file#

sdui.json sits beside module.json: at the root of the module’s repository, and at the root of every archive of a release (wittymodule pack puts it in each one). The server reads it from the version’s folder.

It is read strictly (sdui.ParseModuleUI):

  • at most 1 MiB (1,048,576 bytes);
  • one JSON object, nothing after it;
  • an unknown field anywhere is refused, so a misspelt field is an error, not ignored.

The top level:

FieldTypeRequiredWhat it is
$schemastringnoThe JSON Schema an editor checks the file with, such as ./sdui/kit/sdui-module.schema.json. The server ignores it.
formatstringyesAlways wittymodule-sdui.
formatVersionintyesAlways 1.
modulestringyesThe module’s ID, the same as id in module.json.
catalogintyesThe catalogue revision the file was written against, from 1 to the server’s. A server refuses a file newer than its own catalogue. Today the catalogue is at revision 8. A change to what an existing component or card style shows or does bumps it; only new components, card styles, sources, commands and optional properties are additive (SDUI). Revision 7 changed what the person card style shows (badges), which is why a module that yields person items writes catalog: 7 at least; revision 8 changed what it does (presence dot, no focus without an action unless the list says focusable), and a module whose pages use focusGrow, detail, regions or controls writes catalog: 8.
themeobjectyesThe module’s theme scope.
sourceslistnoData sources the module answers through its helper.
componentslistnoNamed sections of the module’s own: components.
viewslistnoViews an app may draw itself in a NativeView.
pageslistnoWhole pages.
insertslistnoSections put into built-in pages: inserts.
presetslistnoSections for the page editor’s gallery: presets.
navigationlistnoMenu entries.
settingslistnoSettings pages, drawn by each app’s own Settings.

The JSON Schema is sdui-module.schema.json, written from the Go types. The types themselves are ModuleUI and its parts in pkg/sdui/module.go. Where this document and that code differ, the code is right.

Names#

Everything a module adds is named after the module, so two modules never clash and a name always says where it comes from. <module> is the module’s ID: a lower-case letter, then 1 to 63 lower-case letters and digits (wittyboardgames).

WhatFormRuleExample
Page ID<module> or <module>-…Also a valid page ID (lower-case letters, digits, -, _, at most 64), and never a built-in page’s ID.wittyboardgames
Inserted section ID<module> or <module>-…Unique among the module’s inserts into one page.wittyboardgames-tonight
Preset ID<module> or <module>-…wittyboardgames-recent
Menu entry ID<module> or <module>-…wittyboardgames
Settings page ID<module> or <module>-…wittyboardgames
Source type<module>.<camelName>Name: a lower-case letter, then up to 47 letters and digits.wittyboardgames.shelf
View ID<module>.<camelName>As a source.wittyboardgames.scoreboard
Component type<module>.<PascalName>Name: an upper-case letter, then up to 47 letters and digits.wittyboardgames.GameNight
Property or parameter namecamelNameA lower-case letter, then up to 47 letters and digits; never type or map.players
Setting keycamelNameA lower-case letter, then up to 63 letters, digits, _, . and -. Unique across all the module’s settings pages.household

Sections inside a module’s own pages, components and presets need no prefix: they live on the module’s page, or are given their ID by whoever uses them.

Two names are the same thing only within one module: the same name twice in one file is an error (“already used at …”).

Theme#

theme is the module’s theme scope. Its sections, pages and items take the scope’s colours (Theme scopes).

FieldTypeRequiredWhat it is
scopestringyesAlways the module’s ID.
labelstringnoThe name the theme editor shows for the scope, and the title of the module in Settings → Modules. At most 60 characters.
tokensmapnoThe colours the module would like: colour token → colour. A token must be one of the theme engine’s colour tokens (such as accent; see Themes), and a colour #rrggbb, #rrggbbaa, rgb() or rgba().

The module’s tokens are the bottom layer. An administrator’s overrides for the scope (PUT /api/v1/theme/modules/{scope}) replace them token by token. The result reaches apps two ways:

  • in every rendered document, as tokens on each node in the scope and as document.theme for a page in it (Theme scopes);
  • in GET /api/v1/theme, under modules.<module>: tokens is the whole palette with the module’s and the administrator’s colours over it, and overrides is the administrator’s alone. Each look in variants has its own modules too.

A module’s page and every section it inserts default to its scope, and so does every item its sources give.

Sources#

A source is a data source the module answers, so only a module delivered as a helper may declare one: a web bundle or a program with sources is refused at install, because nothing could answer them. Sections use it like any catalogue source: "source": { "type": "wittyboardgames.shelf", "sort": "name" }.

FieldTypeRequiredWhat it is
typestringyes<module>.<camelName>.
labelstringyesWhat the editor calls it. At most 80 characters.
descriptionstringnoAt most 500 characters.
iconstringnoOne of the icons.
paramslistnoIts parameters, as property descriptions.
yieldslistyesThe kinds of item it gives, at least one: movie, episode, show, season, video, disc, album, artist, track, book, audiobook, podcast, game, photo, channel, recording, collection, library, genre, view, person. A person is drawn by the person card style: a photo (or initials), a name, a line (a role, or where they are), badges (presence, a seat), and it opens something only when the item has a route.
cardStylestringyesThe card style a section’s "cardStyle": "auto" means.
pageKindslistnoThe kinds of page it may be used on. Empty: any.
pagedboolnoIt gives more through a section’s cursor URL (Paging).
seeAllstringnoThe route “See all” opens, with {param} placeholders: /page/wittyboardgames.
titlestringnoA good default title for a section using it.
sinceintnoThe catalogue revision it appeared in. 0: the server’s revision.
exampleobjectnoAn example section, for the editor.
topShelfboolnoOffer it on tvOS Top Shelf as a row of its own (Top Shelf).

category and module may be written but are set by the server: in the catalogue a module’s source has "category": "module" and "module": "<module>".

How a source is answered#

Only a module with a running helper can answer a source: delivery: helper (a service is a helper too). The server starts the helper on first use, as for any call (Writing a helper). A web or program module has no helper to ask, so it declares no sources; its sections use the catalogue’s.

For each page of a section’s items, the server calls the helper’s sdui.items method over the helper protocol:

server → {"id":7,"method":"sdui.items","params":{
  "source": {"type":"wittyboardgames.shelf","players":4,"sort":"shuffle","limit":12},
  "offset": 0, "limit": 12,
  "viewer": {"profileKind":"adult","cannot":["recordings"],"formFactor":"phone","platform":"ios","locale":"en-GB"},
  "settings": {"household":4,"ages":"all"}}}
helper → {"id":7,"result":{"items":[ … ],"more":false,"total":12}}

The request (ItemsRequest):

FieldWhat it is
sourceThe section’s source, every $variable filled in and every component placeholder expanded.
filterThe page’s filter and sort parameters, for a filterable source. Left out when there are none.
offset, limitWhich items: skip offset, give at most limit. limit is never more than 500 and never past the source’s own limit.
viewerWho is asking (Viewer): profileKind (adult, kids, guest), admin, cannot (the profile’s parental feature switches that are off), formFactor, platform, locale. Leave out what isn’t for them.
settingsThe module’s settings for this profile: the server’s values, then the profile’s own over them, each with its default. Secrets are included. Left out when the module has no settings.

The answer (ItemsAnswer):

FieldWhat it is
itemsThe items, as Items.
moreThere are more after these.
totalHow many there are in all, when known. A total smaller than offset plus the items is taken as unknown.

A *wittymodule.CallError from the helper (it answered no) puts the section in the error state, with Retry. So does a helper that isn’t running, such as one resting after failures. Any other failure counts against the version, as every call does (What a server does with a release). A section whose source gives nothing is left out, unless it says "empty": "message".

The helper has the same time limit as every call. A page waits for its eager sections, so answer quickly, from what the helper keeps, and page with offset.

Items#

An item is sdui.Item (pkg/sdui/model.go), the same thing the server’s own sources give. The server never trusts it. Before it reaches a card it keeps only this (cleanModuleItem in internal/server/sdui_modules.go):

FieldKept when, and how
idRequired, at most 200 bytes, unique and stable within the source. An item without one is dropped.
kindRequired, one of the kinds the source’s own yields lists. Otherwise dropped.
titleRequired, not blank, cut to 300 characters. Otherwise dropped.
contentRating, genresChecked against the profile’s limits (ratings, genres, kinds of title). An item the profile may not see is dropped.
subtitle, taglineCut to 300 characters.
overviewCut to 2,000 characters.
routeKept when it is a place in the app (/page/wittyboardgames, /item/42); otherwise removed. A card with a route opens it.
imagesOnly poster, backdrop, square and logo, and only paths on this server beginning /api/. Others are removed. The renderer adds the width to ask for.
playId, nextIdKept only when it is the ID of a library item this profile may see and play, and its screen time isn’t over. Otherwise removed. A module can’t make anything playable that isn’t in a library.
canOnly play, download, share, watchLater, watched, playOn, watchParty. Every one of them acts on a title of the library, so an item without a playId that survives the check above offers none.
badgesAt most 3, each cut to 12 characters.
iconKept when it is one of the icons.
scopeDefaults to the module’s ID.
the restyear, rating, runtimeSec, studio, progress, watched, unwatched, resumeSec, season, episode, showTitle, showId, artist, track, count, number, now, next: passed on as given.

Items past limit are cut off, and more is set.

Actions, controls and regions (catalogue revision 8)#

An item a module answers may carry, besides what it always could, action (what its row or card does instead of opening its route), actions (the buttons of a Shelf’s detail panel: {id, label, glyph, action}, at most four), trailing (text at a row’s end) and control (a switch, select, field or slider in a row: see SDUI.md, “Forms and controls”). The server holds them to what a client may run for a tap: a navigate action to a route of the app (as: "layer" shows the page over the screen), play of a title the profile may play, a native screen, back, or a command that is the module’s own (the command’s module in the catalogue is the module’s ID, or its op begins with the ID and a dot), with only the params the command declares, as short strings, numbers or booleans. Anything else is dropped, and an item whose only action was dropped is an ordinary item. A module’s page may also set regions (statusBar items and systemDock entries), which the server sends as document.regions while the page shows. A settings page may declare slot (you.games or people.profile, the latter admin only), and so may a module’s custom page (a page whose rows are not module settings, such as a Form over the profile’s own choices); the server lists both at GET /sdui/slots/{slot} as {module, label, id, title, icon, url} for a settings page and {…, route} for a page, for the hand-built Settings to draw with its generic settings-page renderer or the SDUI renderer. A page in people.profile has ?item={profile} on its route: Settings fills in the profile’s ID as item, and the page’s sources read it as $item.

Top Shelf#

A source marked "topShelf": true is offered on the Top Shelf of the Apple TV app (SDUI.md, Top Shelf): after what the profile was watching and before what is new in its libraries, the server asks it with sdui.items for 10 items, with "source": {"type": "<module>.<name>"} and nothing else, and makes a row of them titled with the source’s title (its label when the title has a {placeholder}). Top Shelf has room for two such rows from every module together; they go in the order of the modules and of each file’s sources, so a module offers the one it means, not all of them. A source that fails or gives nothing has no row, a profile kept from the module gets none, and the items are cleaned as on any page.

Top Shelf is no page and its extension has seconds to answer, so a source offered there:

  • may not have a parameter that is required (it is asked with none);
  • may not have pageKinds (there is no page for $item or $library to come from);
  • should answer from what the helper keeps, quickly, and give items with pictures and a route: an item with no route is left out of Top Shelf, as there’d be nowhere to go.

The first two are checked at install.

Pictures#

A module’s own pictures are served by the server from the helper:

GET /api/v1/sdui/modules/{module}/images/{name}

name is a letter or digit, then up to 127 letters, digits, ., _ and -, with no ... The server calls the helper’s sdui.image method with {"name": "<name>"}, and the helper answers with the picture as the call’s blob (result may be null). The picture must be PNG, JPEG, WebP or GIF, by its content, and at most 4 MiB. The server sends it with its real type, X-Content-Type-Options: nosniff, a sandboxing Content-Security-Policy and Cache-Control: private, max-age=3600. A helper error is a 404, and anything that isn’t a picture a 502.

So an item’s picture is "images": {"square": "/api/v1/sdui/modules/wittyboardgames/images/bg-1.png"}. An item may also point at the server’s own pictures (/api/items/42/poster).

Components#

A component is a named section with properties of its own. It is a template: one catalogue section (with children, if it has them) in which property values are written {{name}}. Administrators find it in the page editor’s palette, and the server expands every use of it before rendering. No app ever sees a module’s component: it is sent the catalogue components it stands for.

FieldTypeRequiredWhat it is
typestringyes<module>.<PascalName>.
labelstringyesWhat the palette calls it. At most 80 characters.
descriptionstringnoAt most 500 characters.
iconstringnoOne of the icons. The palette shows plug when left out.
propslistnoIts properties, as property descriptions.
pageKindslistnoThe kinds of page it may be used on. Empty: any.
sectionobjectyesThe template: a section of a catalogue component.

In the catalogue (GET /api/v1/sdui/catalog) a module’s component appears with "category": "module", "module": "<module>", "expands": "<catalogue component>", the focus and form factors of that component, and an example.

Placeholders#

A placeholder is {{name}}, where name is one of the component’s properties. It may be used in the template’s props and source, and in those of its children, at any depth.

  • Standing alone, "players": "{{players}}", it becomes the property’s value with its type: the number 4, not the text “4”. If the property has no value and no default, the key is left out (and an element of a list is dropped).
  • Inside text, "title": "{{title}} for {{players}}", it is replaced by the value as text. No value: it is replaced by nothing.
  • A property’s value is the use’s, else the property’s default.
  • Every placeholder must name a property (“{{x}} names no property of the component”).
  • Placeholders are not read in id, component, when, repeat, scope or locked.

What a use becomes#

A use is a section whose component is the module’s component: { "id": "night", "component": "wittyboardgames.GameNight", "props": { "players": 4 } }. The server (ModuleSet.ExpandPage) makes it:

Of the resultFrom
component, props, source, childrenThe template, filled in.
idThe use’s.
Children’s IDs<use's id>-<child's id>, cut to 64 characters, so two uses on one page never clash.
whenThe use’s and the template’s together (all); either alone if only one has one.
repeatThe use’s, else the template’s.
scopeThe use’s, else the template’s, else the module’s ID.
lockedLocked if either is.

Rules for a template:

  • It is made of catalogue components only, never of another of the module’s components, so expansion is one step.
  • It must make a valid section when every property has its default or an example value of its type, on the first of its pageKinds (or a custom page). The server checks this.
  • Its sources may be the catalogue’s or the module’s own.

A use on a page (the module’s own or an administrator’s) is checked against the component’s properties like any section. An administrator’s page that uses a component of a module that isn’t in use gets a warning, not an error, and the section is left out until the module is back.

Views#

A view is something of the module’s own that an app may draw itself, in a NativeView: the board games module’s live scoreboard, drawn by its web bundle.

FieldTypeRequiredWhat it is
idstringyes<module>.<camelName>. What a NativeView’s view names.
labelstringyesAt most 80 characters.
descriptionstringnoAt most 500 characters.
platformslistnoWhere it can be drawn, as a hint for the editor: web, tvos, ios, android, androidtv, desktop. Empty: unknown.

A module’s views are added to NativeView’s view options in the catalogue and in nativeViews. An app that can draw a view says so in views= (X-WMS-SDUI-Views, at most 16 names; see What a client sends). That app is sent the NativeView; every other app is sent the NativeView’s children, its fallback. So a NativeView of a module’s view must always have children that make sense on a television.

Commands#

A module’s pages and items run commands: the server’s own (a row’s switch, Watch later), and the module’s own, which it declares under commands. Each is named <module>.<name> and carried out by a request to the module’s own routes, under /api/modules/<module>/; the server lists them in its catalogue (GET /api/v1/sdui/catalog) beside its own, so every app runs them exactly as it runs the server’s, with nothing to update.

"commands": [
  {"op": "wittyplay.core.install", "label": "Install the core", "description": "Downloads a console's core.",
   "method": "POST", "path": "/api/modules/wittyplay/gaming/cores/{item}/install"}
]
FieldWhat it is
op<module>.<name>, not one of the server’s own
label, descriptionWords for the editor and assistive technology
methodGET, POST, PUT, PATCH or DELETE
pathOne of the module’s own routes, under /api/modules/<module>/; {item} and {param} are filled in, URL-escaped
bodyOptional JSON, with {item} and each {param} inside a string (an int parameter’s quotes go)
paramsThe values besides the item: name, type (string, int, bool, ints, object), label, required

A module may declare up to 64. Its items may carry only its own commands and the server commands that name it; the server checks every action an item carries against the catalogue, and the module’s routes check who may do what (a route’s auth, confirm for a password).

Pages#

A module’s page is an ordinary SDUI page, with sections, variants, conditions and all, written in the module’s file. It may use the catalogue’s components and sources, and the module’s own.

Rule
ID<module> or <module>-…, and never a built-in page’s ID.
Kindcustom, library, detail, livetv, music, photos, books or games. Never home, search, libraries or collections: a module adds to Home with an insert.
matchA library or detail page must have match.libraryKind or match.mediaKind: it is for a kind of library or title, never all of them. match.library is refused, since a module doesn’t know this server’s libraries.
scopeDefaults to the module’s ID.

Where it shows:

  • A custom page opens at /page/{id}: /page/wittyboardgames.
  • A page of another kind takes part in choosing the page of that kind (Precedence). A module’s library page with "match": {"libraryKind": "games"} is used for every games library, unless an administrator has a page that matches as well or better.

Precedence, from the top:

  1. The administrator’s pages. One with the same ID as the module’s page replaces it whole. Deleting it brings the module’s back.
  2. The modules’ pages, in order of module ID, each file’s pages in order. Among pages of one kind that match equally, the first wins.
  3. The built-in pages.

So a module’s page beats a built-in page that matches as well, and never an administrator’s.

Inserts#

An insert puts one of the module’s sections into a built-in page: a row on Home, a shelf on the games page.

FieldTypeRequiredWhat it is
pagestringyesA built-in page‘s ID: home, games, library-games, …

  • Inserts go only into built-in pages. A page the administrator wrote, including one that replaces a built-in page, is never changed by a module.
  • The section’s scope defaults to the module’s ID.
  • A section whose ID the page already has is not inserted again.
  • Modules’ inserts are applied in order of module ID, each file’s in order.
  • The section is checked as a section of that page’s kind.
  • After insertion it is an ordinary section: a profile may move or hide it like any other.

Settings#

A module describes its settings. It never draws them. Every app’s own Settings shows them under Settings → Modules → (the module), built with that app’s own controls in that app’s own style. Settings is never an SDUI page and is never sent as a document.

FieldWhat it is

Both PUTs take {"values": {"<key>": <value>, …}}, at most 64 KiB, and answer the same view as GET. Only the keys named change; null removes a saved value, so the default applies again. Every value is checked first, and nothing is saved if one is wrong. A 400 says why, in words to show beside the row:

  • <key>: the module has no such setting;
  • <key>: each profile sets this for itself (a profile key sent to the server’s route);
  • <key>: only an administrator sets this, for the whole server (a server key sent to the personal route);
  • what CheckSetting says: household is between 1 and 12, ages is one of all, kids, listUrl is at most 300 characters, listUrl is one line of plain text, … .

A 403 is a profile that isn’t an administrator writing server values. A 404 is a module that isn’t in use, or one the profile is kept from by its parental switches. A 413 is a profile whose UI document would pass 256 KiB.

What the helper is told#

WhenHowWhat
The helper startsThe environment variable WITTYMODULE_SETTINGSThe server values with defaults, secrets included, as a JSON object.
An administrator changes themThe method settings.changed, {"values": {…}}The same, after the change. Only sent to a helper that is running. A helper that doesn’t know the method may answer with a CallError; it reads the values when it next starts.
Every sdui.itemssettings in the requestThe server values, then this profile’s profile values, with defaults.

Drawing them in an app#

Each app adds Modules to its own Settings, if it hasn’t one already, and under it one entry per module that has settings the profile can see. Inside, each settings page is a screen (or a section, where an app shows one module’s pages together), each group a grouped list with its title as the heading and footer under it, and each row a row of the app’s own:

  • The app’s style, not the module’s. The same controls, fonts, spacing and colours as the rest of that app’s Settings. No module colours here.
  • Read-only when not editable. A server row shown to someone who isn’t an administrator is drawn as a value, not a control.
  • Save as it changes, as the app’s other settings do: a switch or a choice at once, a text field when it is done. A server row goes to the server’s route, a profile row to the personal one. Draw the answer, which is the new state. On a 400, keep the old value and show the message by the row.
  • Secrets are never shown or filled in. Show whether one is set (secretsSet), with a field to type a new one and a way to clear it (null).
  • help is the row’s secondary text or note; unit follows a number.

Accessibility is part of the contract:

  • Every row is reachable without a pointer: by keyboard and Tab on the web and desktop, by the Siri Remote’s focus engine on Apple TV, by the D-pad on Android TV, and by a game controller wherever the app takes one. info rows and read-only rows are reachable too, so they can be read.
  • Every row is labelled for screen readers (VoiceOver, TalkBack, a browser’s reader): its label as the name, its value (with unit) as the value, its help as the hint or description, and its kind as the role (switch, picker, text field, secure field, static text). A read-only row says it is read-only. A group’s title is a heading.
  • Focus moves in reading order: groups top to bottom, rows in order.
  • An error is announced when it is shown.

What the server checks, and when#

sdui.ValidateModuleUI checks everything above: the format, the module’s ID and catalogue revision, the names, the limits, every source, component, view, page, insert, preset, menu entry and settings row against the catalogue and the module’s own file, and the colours against the theme engine. A file is refused when it has an error. Warnings don’t refuse it.

WhenWhat happens to a file that fails
Install (after step 4 of What a server does with a release, once every file has been checked)The version is held for an administrator’s go-ahead (kind incomplete), and the module stays on the version it had. With the go-ahead it runs without its SDUI.
Every time a version is picked for use: at start, on a switch, when a module is turned onThat version isn’t used. The one before takes over, or the module goes without, and the reason is shown on the Modules page.

The refusal says what is wrong, in one of these forms:

  • it is built for module API 4, where a module carries its own SDUI, and it has no sdui.json
  • sdui.json is 1200000 bytes; the most is 1048576
  • sdui.json can't be read: json: unknown field "script"
  • sdui.json has something after its end
  • its sdui.json has data sources, and only a helper can answer them; it is delivered as "web"
  • its sdui.json doesn't fit this server's catalogue: /pages/0/sections/1/component: …; … (the first three errors, each with its JSON path)

On every render, a section of a module that isn’t in use (turned off, not installed, or one the profile is kept from) is left out, and the rest of the page is drawn. The page validator gives an administrator a warning for it.

What apps need to do#

A renderer needs almost nothing new. It only ever sees catalogue components: a module’s components arrive expanded, its sources arrive as cards, and a section of a module that isn’t there is never sent. The conformance fixtures below prove it.

The tasks for each app:

  1. Announce the module views it can draw, in views= with its own. The web app draws a module’s view with the module’s web bundle: it sends the IDs of the views of every bundle it has loaded, and when the page holds a NativeView of one, mounts the bundle’s component for it in that place. A bundle exports views, components by view ID, as it exports pages: export const views = { 'wittyink.bookshelf': Bookshelf }. The web app mounts one with the props { host, view, library?, ...the node's other props }, where host is the object a module’s pages get and view the view’s ID; when the bundle or the export is missing, it draws the node’s children, the fallback, as for any view it doesn’t have, and so it does when the view fails while drawing. GET /api/v1/modules/web names each bundle’s views (views), so the app knows them without loading the bundle. A native app sends a module’s view only if it really draws it; usually it sends none, and its users see the fallback.
  2. Draw module settings in Settings → Modules, as in Drawing them in an app, when the server lists module-settings. GET /api/v1/sdui/modules/settings lists the modules with settings the profile may see, for any profile; for each, GET …/settings gives the pages and values.
  3. Read module palettes from /api/v1/theme: modules.<module>.tokens (and each variant’s modules) for anything of a module the app draws outside a document, such as a module’s own screen or a web bundle’s view. Inside a document, nodes already carry tokens.
  4. Nothing else changes: scope and tokens on nodes, fallbacks, states and paging are as in Rules for renderers.

Writing the file#

A module written in Go#

A helper module imports github.com/wittywilla/wittymodule/sdui, builds its definition in Go (sdui.Module and its parts are copies of the server’s types, so a module needs nothing of the server’s), and keeps sdui.json equal to it with a golden test. The package checks the definition as the server will, as far as that can be done without a server (sdui.Check), and writes it the same way every time (sdui.JSON, sdui.WriteFile). It also helps answer sdui.items, sdui.image and settings.changed in the helper.

// ui.go: the module's SDUI, in Go.
func UI() *sdui.Module { return &sdui.Module{Format: sdui.Format, FormatVersion: sdui.FormatVersion, Module: "wittyx", Catalog: sdui.CatalogRevision, /* … */} }

// ui_test.go: sdui.json is the definition, and the definition passes.
func TestSDUIFile(t *testing.T) {
	if err := sdui.Errors(sdui.Check(UI(), "wittyx")); err != nil {
		t.Fatal(err)
	}
	want, _ := sdui.JSON(UI())
	got, _ := os.ReadFile(sdui.File)
	if !bytes.Equal(got, want) {
		t.Fatal("sdui.json is out of date: write it again from UI()")
	}
}

A web-bundle module#

A web module writes sdui.json by hand, or builds it with kit/sdui/wittymodule-sdui.ts, which kit/module-kit.sh copies into its repository, and writes the result to sdui.json in its build.

Either way#

  • wittymodule check reads sdui.json beside module.json and checks it as the server will. A module built for API 4 without one fails.
  • wittymodule pack puts sdui.json in every archive of the release.
  • The server is the last word: its catalogue and the theme engine’s colour tokens decide. Test against a server (Migrating a module to API 4).

The worked example, end to end#

module-boardgames.json is a module that keeps a household’s board games. Part by part:

The header. "format": "wittymodule-sdui", "formatVersion": 1, "module": "wittyboardgames" (its module.json has the same id), "catalog": 2.

The theme. {"scope": "wittyboardgames", "label": "Board games", "tokens": {"accent": "#2E7D32"}}. Everything of the module is green unless an administrator sets PUT /api/v1/theme/modules/wittyboardgames to something else. “Board games” is its name in the theme editor and in Settings → Modules.

The source. wittyboardgames.shelf gives game items in the square style, takes players (0 to 12), sort (name, played, shuffle) and limit, is paged, and its “See all” opens /page/wittyboardgames. The module’s helper answers it:

server → {"id":3,"method":"sdui.items","params":{"source":{"type":"wittyboardgames.shelf","players":4,"sort":"shuffle","limit":12},
          "offset":0,"limit":12,"viewer":{"profileKind":"adult","formFactor":"tv","platform":"tvos","locale":"en-GB"},
          "settings":{"household":4,"ages":"all"}}}
helper → {"id":3,"result":{"items":[{"id":"bg-1","kind":"game","title":"Harbour Lights","subtitle":"3–5 players",
          "images":{"square":"/api/v1/sdui/modules/wittyboardgames/images/bg-1.png"},"route":"/page/wittyboardgames"}, …],"total":6}}

The server keeps those items as they are: their kind, title, picture path and route all pass. The card’s picture is fetched from the helper with sdui.image {"name": "bg-1.png"}.

The component. wittyboardgames.GameNight has title (default “Game night”) and players (default 4). Its template is a Shelf titled "{{title}} for {{players}}", large cards, “See all” always, with the source {"type": "wittyboardgames.shelf", "players": "{{players}}", "sort": "shuffle", "limit": 12}. A use {"id": "night", "component": "wittyboardgames.GameNight", "props": {"players": 4}} becomes:

{ "id": "night", "component": "Shelf", "scope": "wittyboardgames",
  "props": { "title": "Game night for 4", "cardSize": "l", "seeAll": "always" },
  "source": { "type": "wittyboardgames.shelf", "players": 4, "sort": "shuffle", "limit": 12 } }

players is the number 4 in the source, because it stands alone; it is text in the title.

The view. wittyboardgames.scoreboard, drawn by the module’s web bundle, for web and desktop.

The page. wittyboardgames, kind custom, at /page/wittyboardgames: the GameNight row, a Shelf of every game by name, and a NativeView of the scoreboard whose child is a Notice, “The scoreboard is on the web app.” An Apple TV is sent the notice (module-page-tv); a browser that loaded the bundle and sent views=wittyboardgames.scoreboard is sent the NativeView (module-page-web).

The insert. On Home, after jump, the section wittyboardgames-tonight: a GameNight with its defaults, shown only on Fridays and Saturdays ("when": {"weekday": ["fri", "sat"]}). It is expanded like any use, with the use’s condition. If an administrator has written their own home page, it isn’t inserted.

The preset. wittyboardgames-recent, “Board games played lately”: a Shelf of the source by played, limit 20, in the editor’s gallery.

The menu entry. wittyboardgames, a page entry for its page, behind More on phones and televisions and in the bar elsewhere, placed just before Settings. It takes the page’s title and icon: “Board games”, game.

The settings. One page, “Board games”, in two groups. Under “The shelf”, for the server: listUrl (text, at most 300), apiKey (a secret) and household (a number from 1 to 12, default 4). Under “For you”, with the footer “Each profile chooses its own.”: ages, a profile’s own choice of “Everyone” or “Children”, default all. Every app shows the page under Settings → Modules → Board games. An administrator sets listUrl and apiKey; a profile chooses ages. The helper starts with WITTYMODULE_SETTINGS={"household":4} (and listUrl and apiKey once set), hears settings.changed when an administrator changes them, and gets "settings": {"household": 4, "ages": "all"} with each question about its source.

Migrating a module to API 4#

For each module repository:

  1. Raise api to 4 in module.json, with the WittyModule that speaks API 4.
  2. Write the module’s SDUI.
    • A Go module: build it in Go with github.com/wittywilla/wittymodule/sdui, and write sdui.json from it.
    • A web-bundle module: write sdui.json by hand, or with kit/sdui/wittymodule-sdui.ts (run kit/module-kit.sh to copy it in).
    • Move what the module drew in the apps into it: its pages, its rows on Home, its menu entries, its colours. A module with nothing to add carries the smallest file.
    • Name everything after the module (Names).
  3. Add the golden test (Go): sdui.json equals the definition, and the definition passes sdui.Check.
  4. Answer sdui.items in the helper if the file has sources, and sdui.image if its items show the module’s own pictures. Give each item an id, a kind from the source’s yields, a title, and pictures under /api/v1/sdui/modules/<module>/images/. Page with offset and limit, and leave out what the viewer shouldn’t see.
  5. Describe its settings under settings, choose server or profile for each, and read them from WITTYMODULE_SETTINGS, settings.changed and each request’s settings. A web module’s settings that the bundle drew itself become rows here.
  6. Run wittymodule check on the folder, and fix what it says.
  7. Try it on a server. Build the server against your checkout with node scripts/dev-modules.mjs <Repo>=<your folder>, install the module from a test catalogue (Developing a server and a module together), and check: the install isn’t refused; its page, rows and menu entry appear on the web app and one television app; its sections fill; its settings show under Settings → Modules and save.
