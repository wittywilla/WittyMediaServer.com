Measuring FFmpeg

How to measure what FFmpeg costs the server when something plays, so that a change to how it’s run can be judged by numbers before and after. This is for people working on the server; it changes nothing for someone using it.

Changed 18 November 2026 Edit on GitHub
On this page
  1. What it measures
  2. Running it
  3. Settings
  4. Reading the numbers
  5. Figures

What it measures#

TestFFmpegBench in internal/server/ffbench_real_test.go plays real files the way a viewer does: it asks POST /api/items/{id}/playback (or opens a disc’s title, or starts a channel’s live session), fetches the playlist and the first segment, then the next segments in order, and then seeks. It runs a real server with its own data folder and reads the media without writing anything beside it. It does nothing unless WMS_FFBENCH=1 is set.

CaseWhat plays
remux-h264-1080pA 1080p H.264 film in Matroska, as a browser gets it: the picture copied into HLS, the sound converted to AAC
x264-1080pThe same film converted to H.264 at its own size
x264-1080p-to-720p-4MThe same, at 720p within 4 Mb/s, as for a slow remote connection
hevc-1080p-to-h264A 1080p HEVC episode converted to H.264
tonemap-4k-hdr-to-1080pA 4K HDR film, mapped to an ordinary picture at 1080p
burn-text-subtitlesA film with a subtitle file beside it, drawn into the picture
burn-picture-subtitlesA film with picture subtitles (Blu-ray or DVD style), drawn into the picture
audio-transcodeA long sound file converted to AAC for a player that can’t play it
live-channel-1080pA TV channel’s live session on a 1080p file, for 30 seconds at viewing speed
dvd-titleA DVD image’s main title, through the WittyDVD module
bluray-titleA Blu-ray image’s main title, through the WittyBluray module

Each case looks through the media folders for the first file that fits: the right codec and size, at least two minutes long. Encrypted discs are passed over, since the server refuses them. A case with nothing to play is skipped. The disc cases need the real modules (see Running it) and are skipped without them.

Running it#

It reads D:\WittyDemoMedia and D:\ServerMedia on Windows, and /mnt/d/WittyDemoMedia and /mnt/d/ServerMedia elsewhere, unless told otherwise. From the repository’s folder:

On Windows, in Git Bash:

WMS_FFBENCH=1 WMS_FFMPEG=$PWD/.tools/ffmpeg-master-latest-win64-gpl/bin/ffmpeg.exe WMS_FFPROBE=$PWD/.tools/ffmpeg-master-latest-win64-gpl/bin/ffprobe.exe go test ./internal/server -run TestFFmpegBench -v -count=1 -timeout 120m

On Linux, macOS and FreeBSD, with FFmpeg on the PATH:

WMS_FFBENCH=1 go test ./internal/server -run TestFFmpegBench -v -count=1 -timeout 120m

The table comes at the end. For the disc cases, make a catalogue of the two modules first (in WSL, or Git Bash on Windows, which builds them for Windows) and name it in WMS_TEST_CATALOG:

scripts/make-test-catalog.sh /tmp/wms-catalog /mnt/d/projects WittyDVD WittyBluray

A whole run with three runs of each case took 40 minutes on the laptop under Figures, with other work on it.

To compare two versions, build each one’s test program and run them one after the other on the same machine with the same settings, ideally twice, alternating. Other work on the machine changes the timings a lot; it changes memory much less.

go test -c -o bench-before.exe ./internal/server

Settings#

VariableWhat it doesDefault
WMS_FFBENCHRuns it at alloff
WMS_FFMPEG, WMS_FFPROBEWhich FFmpegthe one beside the program, then the PATH
WMS_FFBENCH_MEDIAMedia folders to look in, in order, separated as the PATH is (; on Windows, : elsewhere)see above
WMS_FFBENCH_RUNSRuns of each case3
WMS_FFBENCH_SEGMENTSSegments timed after the first, for the speed8 (32 seconds)
WMS_FFBENCH_ONLYA regular expression: only the cases it matchesall
WMS_FFBENCH_SETTINGSServer settings as an administrator would set them, such as hwEncoders=h264_nvenc,lowPower=1. The hardware encoders are tested first, as the server does, and the first that works is used unless they’re named or turned off with hwEncoders= (nothing after it), which measures libx264none: any hardware encoder that works
WMS_FFBENCH_OUTA JSON file for every run’s numbers, the machine and the FFmpeg versionnone
WMS_TEST_CATALOGThe module catalogue, for the disc casesnone

Reading the numbers#

Each cell is the median of the runs, with the lowest and highest in brackets.

ColumnMeans
Start msThe request that sets playing up: probing the file and deciding. For a disc it’s opening it and reaching its title
First segment msFrom that request to the first segment in hand, which is about how long a viewer waits for the picture
Speed ×Times real time, over the segments after the first. A copy is held to 4 times real time on purpose, and a channel to real time
CPU s per minProcessor seconds, over every core, that FFmpeg and ffprobe used for each minute of what was played. 60 means one core kept busy
Peak MBThe most memory the largest FFmpeg process held at any moment (peak working set on Windows, VmHWM on Linux)
Seek msThe time to the first segment after a jump to 40% and to 70% of the way in, on average. A copied stream starts a new stream there, as players do

Things that mislead:

  • The first run of a case reads the file from disk; the others find it in the system’s cache. A film nobody has opened lately behaves like the first run.
  • Other work on the machine slows FFmpeg down: a build, a scan or other tests. Run comparisons back to back and report the spread. On a busy Windows machine even starting FFmpeg can take seconds, because the 170 MB program is scanned each time.
  • A copy’s CPU includes converting its sound, and the subtitle tracks a web player is offered, which are read in the background from the whole file.
  • Memory grows with the machine’s core count. FFmpeg and libx264 start more threads on a bigger machine, and each thread holds pictures.
