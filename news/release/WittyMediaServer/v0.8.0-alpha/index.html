Release notes

What’s new in 0.8.0-alpha

Released 2026-11-16.

Highlights. This release is Design 2 and what it needs from the server.

  • Design 2. The old design is gone, with no fallback. Fourteen looks (experiences: Lumen, Rail, Stage, Aero, Classic, Classic Cable, Classic Satellite, Compact, Paper, Marquee, Crossbar, Big picture, Dashboard, Retro), chosen by an administrator’s policy, by a profile for each device, or required of a profile, each described as data (including wire, its layout in a few words, for the pickers). Fifteen themes, any with any look, with import, a profile’s own colours and contrast warnings. The server’s name keeps its own colours and mark in every look and theme. See docs/design-2 and Themes.
  • First run is fourteen steps in a web browser, and only there: until it is finished the server answers apps with setup_required, while the wizard’s own browser calls pass the gate. The server’s time zone is a setting.
  • Server-driven UI, catalogue revision 8: every component and card style drawn by every app, forms and controls, regions (status bar and system dock), layers, QR codes, module pages in Settings slots, person cards with presence, and the conformance fixtures every renderer proves itself against. Modules carry their own SDUI, and the module kit follows the catalogue.
  • WittyPlay Online: friends, open rooms, seats, memories (saves and screenshots) and their commands, on the same data sources as every other page.
  • Standalone apps (WittyReader, WittyMediaPlayer) use the server-driven UI and wear the themes where that is built; the rest is listed in docs/plans/DESIGN-2-RELEASE.md.
  • The rest of this section is everything else added since 0.7.2-alpha, newest first.
  • Each rotating channel has an order of its own (#354). A channel set to rotate took its shows in the same order as every other, ignoring its seed, so two channels rotating the same shows built identical days. Each now rotates in its own order, the same on every turn; rotating channels made before change order once.
  • Crossbar’s categories each have their own icon, and a title page has no line under the top bar (#357). Featured, Your libraries, Jump back in, On TV now, Recommended, Next up, Saved views, Recently added and the rest take an icon from the catalogue’s set (so every app draws them; list stays for anything else). The top bar’s soft edge waits until a page with a backdrop scrolls under it, in every browser.
  • First-run setup asks for language and time zone (#352). The Name step’s Language and time starts on the browser’s language and sets disc menus and the sound track a title starts with (menuLanguage, audioLanguage), or keeps each title’s original; subtitles stay off. A new time zone takes effect when setup is finished, with one restart of the server then. The server’s own pages are English for now.
  • wittyconnect join (#349): the desktop app can offer Join from away, as the Android and Apple apps do, through the same pkg/wittyconnect.Join. The key goes down the pipe, never on the command line; events are code, then joined or error (expired after fifteen minutes). wittyconnect version says wittyconnect 2 (Peer to peer).
  • Windows and Linux pass (#343). A module’s service and helper are stopped before its folders are removed or replaced (uninstalling, removing in first-run setup, or reinstalling over the same version), so Windows no longer refuses to delete files still in use. A helper that leaves cleanly on Windows (ERROR_NO_DATA, ERROR_BROKEN_PIPE) is started again instead of counted as a crash. Changing the server’s time zone restarts it once, without a race. Every text file checks out with LF. On a Mac, CI builds the tray app in a folder of its own, so a disk that ignores case no longer lets it replace the server’s program. The installers have new artwork, and the snap is packed where snapcraft can write.
  • A game opened from its item page starts once. Going from a page in the app’s frame to a full-window module screen (an item page’s game to /game/<id>) drew the game, then drew it again inside WittyPlay’s card Provider when that arrived once the page was idle, so a second session started and stopped the first (“started on another device”). The web app now keeps the module registrations that have arrived where every part reads them at once (moduleRegistry.tsx): a frame drawn after the bundle has the Provider from its first render, and the full-window frame holds its screen back until the card owner’s bundle is in. npm run test:cards (in CI) renders it.
  • A page with a scan on it counts up by itself. A rendered SDUI page carries meta.refreshSec while something it shows is in progress (any data source can ask; libraryScan and libraryAdmin do while a library is scanning, every 2 seconds) and leaves it out once nothing is busy. Clients ask for the page again that long after each answer, quietly and only while it is open and showing, so Scan the library and the libraries’ list settle on “Last scanned” without being reopened (docs/SDUI.md). The web app does this on pages and layers.
  • The server takes module API 5 only. A module version built for API 3 or 4 isn’t installed, even with an override, and isn’t used: every stock module is on API 5, and the server’s own kinds of media are listed as builtin modules of API 5. What was kept for older versions is gone: the loader’s older-API branches, and the one-off repairs of WittyPlay 0.3 versions a Mac’s sandbox or a failing game took out of use, with the state they saved. The host API’s Item says versionOf and versionLabel for another version of an item. WittyPlay’s server-wide settings (Settings, Consoles & cores) are WittyPlay’s own, at /api/modules/wittyplay/gaming/settings; the server’s /settings never kept them.
  • Scans never time out on their own, and every library has Scan for changes and Full rescan. A scan runs until it is done or someone stops it (the 30-minute limit on a module’s scan call is gone, and a module’s service answering a call is no longer stopped as idle after 5 minutes, which ended long calls); what stops one by itself is nothing moving for 10 minutes, and it fails saying what it was waiting for. The walk, each module call and a module’s own reports count as moving: a module answering a scan call reports with the host’s Task named scan-<library> (WittyPlay does), which the scan’s task shows (“Putting what was found together: 12,400 of 16,780 files”) and which is never a task of its own. POST /api/libraries/{id}/scan takes {"mode": "changes" | "full"}: Scan for changes (the default) reads only new, changed or removed files; Full rescan reads every file and its details again from scratch, and a module scanning the library is told so (scan: {mode, since} in the host’s libraries) and describes every item with refresh. Every scan is written down as it starts (migration 39: library_scans, and scan_describe for the items still to be described), so a scan a restart cut short carries on when the server is back, a Full rescan from where it got to. Libraries carry scanMode while one runs; scan progress carries mode and resumed. On the web every scan control offers both, and SDUI has library.rescan and the page manage-library (/manage/library/{id}).
  • WittyVisualizer, WittyStats and WittyIntegratedFileBrowser are on module API 5 (0.4.0, 0.3.0 and 0.4.0), each with integration.json. None has routes or data of its own: the server keeps the numbers and who sees them (/api/system/metrics…), GET /api/fs with its checks of the file browser’s answers and the typed path when it is missing, and the audio player’s visualizer place. The catalogue’s music.visualizer is now only defaultOn: the effects and their controls (presets, controls) are gone from the server, and every app lists them from WittyVisualizer’s settings page (GET /api/sdui/modules/wittyvisualizer/settings). On TV and phones, Statistics is WittyStats’ page (/page/wittystats) and Server folders WittyIntegratedFileBrowser’s (/page/wittyintegratedfilebrowser, administrators only, ?name=<folder> to open one). The web app now passes a custom page’s item, name and of from its address (/page/<id>?name=…), so a module page opened about something shows it there too.
  • Albums, the photo map’s online map and the gallery’s screens are WittyPhotos’ own (module API 5); readers come from the readers hook. WittyPhotos answers /api/modules/wittyphotos/albums… and /map from its own database and settings (/api/photos/albums… is gone, with no aliases), and draws the gallery (timeline, albums, favourites, folders, map, viewer) as its web part: a photos library opens at /photos/library/{id}. A migration (36) drops the server’s album tables and map settings; WittyPhotos starts empty. The server keeps scanning, EXIF, pictures, uploads and share links: GET /api/photos/list and /months take ids=, and a share link can share a set of pictures ({kind: "photos", ids, title}, as an album is when the link is made) in place of an album. The scans ask WittyPhotos for EXIF, sizes and RAW previews as service calls. A book opens in whichever module’s integration.json claims its format (WittyEbook, WittyPDF, WittyComics at 0.4.0), on WittyInk’s kit; the app’s format-to-module map, its own books library and book pages (Books.tsx) and the About page’s empty readers list are gone. The built-in books pages give way to WittyInk’s while it’s in use.
  • Discs and audio CDs are their modules’ own (module API 5). A disc’s page, why a title is its film, an administrator’s choice of another and the names of its titles are WittyDVD’s and WittyBluray’s routes, under /api/modules/wittydvd/discs/{id} and /api/modules/wittybluray/discs/{id} (/api/items/{id}/disc, its /labels, /analysis and /choice, and /api/bluray/capabilities are gone, with no aliases), and their sections on a title’s page are answered by the modules, whose rows run their own commands (disc.choose, disc.clearChoice, disc.rank and disc.compare are gone from the catalogue). The names of titles and chapters are kept in each module’s own database, starting empty: a migration drops the server’s disc_labels column. The disc player, Settings’ DVDs and Blu-rays (out of Playback, which is now just Playback) and a disc’s Disc settings and names are WittyDisc’s web part, which WittyDVD and WittyBluray bring. The CD player and its engine are WittyCD’s, and finding what a CD is moved to /api/modules/wittycd/cds/{id}/matches and /identify (/api/cd/{id}/matches and /identify are gone); on TV, the SDUI page wittycd-identify. What stays the server’s: the disc sessions and their streams, the scramble and AACS guards and every check of an engine’s answers, the disc’s ranking and choice of film on its item, the scan, CD audio through FFmpeg and covers. The host API gains /discs/{id} (with page and rank), /discs/{id}/rank, /discs/{id}/choice, /discs/libbluray, /cds/{id}/matches and /cds/{id}/release. A disc module’s service process may reach the host API; the helpers that read discs still have no network.
  • Tuners, their channels and guide sources are WittyTuner’s own (module API 5). Their routes are the module’s, under /api/modules/wittytuner/ (/api/tuners, /api/tuner-channels, /api/epg and /api/tv/encrypted-help are gone, with no aliases), as are Settings → Live TV & tuners, the first-run step “Live TV” and the encrypted-channels page; WittyTuner’s sdui.json has the same for every app’s TV. A WittyTV migration (9) drops tuners, tuner_channels and epg_sources, and with them the guide’s programmes and what named the old channels (scheduled recordings, series rules, favourites, reminders and set entries of tuner channels): WittyTuner starts with an empty database. The guide, recordings, catch-up, favourites and sets stay the server’s, which opens every channel through WittyTuner’s service and guards every stream itself; WittyTuner hands each guide it fetches to the host API (POST /host/v1/tv/guide/{source}). Channel health checks leave the server’s diagnostics with the rest of the tuner settings.
  • Game PCs and game rigs are WittyCouch’s and WittyRigs’ own (module API 5). Their routes are the modules’, under /api/modules/wittycouch/ and /api/modules/wittyrigs/ (/api/couch, /api/rigs and /api/wittyrigs are gone, with no aliases), as are their pages, Settings sections, settings and data: each keeps its own database, starting empty (the server’s wittycouch_hosts and wittyrigs_* tables, their settings and the libraries of rigs added before are dropped). The host API adds held libraries (POST /libraries, PATCH/DELETE /libraries/{id}, PUT /libraries/{id}/items, DELETE /items/{id}, PUT/DELETE /items/{id}/poster), GET /programs/{id} and the event library.removed; module routes are told X-Witty-Limited, X-Witty-Reached and X-Witty-Machine. /capabilities no longer lists game-rigs.
  • A module version made for an older server is never installed without a warning. One whose own range stops below this server (WittyPlay 0.3.6, maxServer: 0.6.x, on 0.8.0-alpha) may still start, but its pages, settings and features from this server can be missing. Automatic updates, Update All, “latest”, first-run setup, restore and repair never pick one; with nothing made for this server they say “No version of WittyPlay for this server is published yet”. The store, Settings → Modules, first-run setup and a setup step’s “add the module” open a pop-up first (Don’t install is the default; one pop-up with a choice for each when setup installs several), and only Install anyway sends confirmOlder; without it the install routes answer 409 older-server naming each version. One already in use says so in Settings → Modules and the store, with the newer version or Remove. docs/MODULES.md, “Version ranges”.

The Reader page hands WittyInk and the readers the profile’s settings of those modules (ReaderHost.settings), so what is chosen in Settings, Modules and what is chosen while reading are the same on every device. A book’s page has its Read button again on the web and desktop apps (server-driven pages had none): Read, Continue reading or Read again, and Read from the start. Apps without the readers aren’t offered it.

Clients that keep their own card-style table check it against pkg/sdui/conformance/card-style-table.json. Documents say catalog: 7; every fixture is regenerated (the only change in each is that number, apart from the people fixtures).
  • A timeZone setting (an IANA name) for the server’s time zone, applied at once and empty to follow the computer; GET /settings also says timeZoneNow and timeZoneComputer. Time zone data is built in, so it works on Windows and small containers.

  • Cast and crew for every film, show and episode (Cast and crew). The library now keeps people: the cast with their parts, guest stars on episodes and the crew by department (Directing, Writing, Production, Camera, Lighting, Editing, Sound, Art with production design and set decoration, Costume & Make-Up, Visual Effects, Crew), from NFO files (<actor>, <director>, <credits>, <producer> and the rest, as media centres write them), TMDB, TheTVDB, TVmaze and a file’s own tags, each part from the best source that has it, each person kept once across titles.   • Module overrides: an administrator can install a module the server would otherwise refuse on a judgement, knowingly (Installing past a rule). The kinds are an unfinished version (its status is experimental or incomplete, or a module API 4 version whose SDUI is missing or fails, which then runs without it), compatibility mode outside a version’s server range, a file, a module this server doesn’t know, a key it doesn’t trust, Apple’s weaker sandbox, and no signature. Each needs a go-ahead naming exactly what is bypassed, the password again, and from the third severity the module’s name typed; it is shown as Overridden, written to the module audit log, never updated by itself, and taken back in one step. Someone else’s code keeps no permissions but those ticked, in the strict sandbox. On a Mac, forks and other publishers’ modules now run inside Apple’s sandbox with that override, and never outside it. What can’t be overridden (a module API this server doesn’t speak, a withdrawal for security, WittyTuner’s replacement, WMS_NO_MODULE_FORKS=1, no sandbox at all) is still refused with the reason. Start one from a title’s page, give people its six-letter code, and everyone’s player stays in step wherever they are: one state on the server, starts set a moment in the future, each player’s clock measured against the server’s, small drift closed by playing 3% faster or slower and large drift by seeking. A host with hand-over, “everyone can control”, late joining, two minutes to come back to a dropped seat, and no way to see anything an account’s limits don’t allow. With either, only an administrator may ask for it now (others get 403 with reason admin-only or off, and a song’s stems listing says so); with Automatically, one account may ask 40 times an hour, as karaoke’s own requests may (429 rate-limited).
